# p05

**Prompt:**
> My cofounder wants to rewrite the backend in Rust. His argument is the Node service is already showing latency problems under load and we'll have to do it eventually anyway. I think it's a 6 week detour. Help me think about this — and if I'm wrong I want to know.

_Context: Cofounder disagreement about the backend stack, mid-week_


## Candidates (8)

- **The Great Rewrite** [block] — A rewrite discards the accumulated bug fixes encoded in the old code — each ugly branch is a defect someone found in production — while the old system keeps needing maintenance, so the team pays for two systems and ships neither. TRIGGER: A prompt or issue proposing to "rewrite from scratch", "start clean", "greenfield it", or replace a working subsystem wholesale because the code is messy.
- **Second-System Rewrite** [block] — A rewrite is scoped against the accumulated wishlist of everything the old system got wrong, so the new system is strictly larger than the one that already took years. Meanwhile the old system keeps shipping nothing, and the rewrite's real cost is the undocumented edge cases embedded in the code being discarded. TRIGGER: A proposal to rewrite a working module or surface from scratch, justified by cruft, where the new version is also scoped to fix known limitations of the old one.
- **Guessing The Bottleneck** [warn] — Intuition about performance is trained on the code you read, while cost lives in behavior you cannot see — allocation, cache misses, scheduler and GC intervals, tail latency. Optimizing before profiling spends effort on the wrong axis and hides the real cause behind a changed baseline. TRIGGER: A diff or plan doing performance work — caching, batching, async, index, language/runtime swap — with no profile, benchmark, or production measurement cited, or a claim that something "should be faster".
- **Innovation Token Overdraft** [warn] — Every unfamiliar technology carries unknown failure modes that only surface under production load, and each one consumes the same scarce resource: engineer attention during incidents. Spending several at once means every outage has multiple novel suspects and no one has intuition about any of them. TRIGGER: A diff or spec that introduces a new datastore, language, queue, or orchestration layer — especially two or more in the same change — where an already-running component would do.
- **The Inside-View Estimate** [warn] — An estimate built by decomposing the specific task counts only the steps you can currently see, and the steps you cannot see are exactly the ones that consume the schedule. Decomposition feels more rigorous than a base rate, so it displaces the base rate rather than being checked against it. TRIGGER: A plan, spec, or roadmap states a duration, ship date, or phase count derived by listing the work, with no reference to how long a comparable past effort actually took.
- **Numbers Nobody Measured** [block] — A quantitative claim with no measurement behind it still functions as one downstream — it gets cited, budgeted against, and used to close arguments — because the number's format carries authority its provenance does not. Organizations generate these numbers where the desired answer is known and the measurement is expensive. TRIGGER: A spec, README, or marketing line quotes a reliability, latency, uptime, accuracy, or coverage figure without naming the measurement that produced it.
- **Preference-First Framing** [warn] — When the decision-maker states their conclusion before soliciting input, every subsequent contribution is scored by the contributor against the cost of contradicting them, not against the evidence. Input arrives, so the process looks consultative, but it has been filtered to what survives disagreement with the boss. TRIGGER: A request to review, sign off on, or implement an approach whose author has already stated a preferred outcome, or a message shaped as "here's what we're doing — thoughts?"
- **Chasing The Moving Baseline** [warn] — Rescoping in-flight work to adopt a newer substrate resets the completion clock while the substrate keeps advancing, so the gap between what you have and what is current never closes — each adoption is individually justified and the sequence never terminates. TRIGGER: In-flight work is rescoped to adopt a newly released model, framework, engine, API version, or internal abstraction before the current version has shipped to anyone.
