# p03

**Prompt:**
> the settings page feels cluttered and I hate looking at it. there are like 14 rows now and half of them are things nobody touches. clean it up

_Context: Just came back to a settings screen that has grown organically for months_


## Candidates (6)

- **Signifier Erasure** [warn] — Flattening removes borders, fills, and shadows — which are not decoration but the clickability cues users scan for — so the visual noise drops while the search cost rises; the page looks calmer in a screenshot and costs more per task in use. TRIGGER: A diff removes borders, background fills, underlines, or shadows from interactive elements, converts buttons to text/ghost buttons, or a spec asks to "make it cleaner / flatter / less chrome."
- **Relearning Tax Ignored** [warn] — In a product people use daily, the interface is a motor habit; moving things resets that habit for every existing user at once, so the cost is paid on day one by everyone while the benefit accrues slowly to newcomers who do not exist yet. The new-user gain almost never exceeds the aggregate relearning loss. TRIGGER: A spec reorganizes navigation, moves an existing feature to a new location, renames a primary action, or changes the information architecture of a product that already has habituated daily users.
- **Chesterton's Dead Code** [block] — Code that appears unused is often reachable through a path nobody has in mind — an old flag, a stale server, a legacy client — so removing the guard while leaving the code, or reusing its switch for a new meaning, arms a landmine that only fires under partial deployment. TRIGGER: A diff that deletes or repurposes a feature flag, retry, guard clause, or branch labeled unused/deprecated/legacy without explaining what originally set it.
- **Control Swallowed By Screen** [warn] — A screen control demands visual attention and offers no tactile confirmation, so moving a frequent or eyes-busy action into a menu converts a sub-second muscle-memory operation into a look-navigate-aim-verify loop. The cost is invisible in a demo where the user is already looking at the screen. TRIGGER: A spec relocates a frequent, urgent, or eyes-busy control into a screen, menu, submenu, command palette, or gesture — replacing a dedicated key, button, or always-visible affordance.
- **Discoverability Mistaken For Absence** [note] — Users request features they cannot find, so a request queue reads as a gap list when it is often a findability report; building the requested thing a second time adds surface area without adding capability and makes the original even harder to find. TRIGGER: A ticket or spec proposes building a capability that may already exist somewhere in the product — "add a way to X," "users can't do Y" — without a check of whether X/Y already ships behind a menu, flag, or command.
- **Curated Demo Data** [warn] — Designs validated on hand-picked content encode assumptions about length, density, freshness, and correctness that real data violates on day one; the demo proves the layout, not the product, and the gap surfaces publicly at launch scale. TRIGGER: A design, screenshot, or demo uses seeded, curated, or short sample data; or a spec has no defined empty state, long-string, stale-data, error, and high-volume case for the surface being built.
