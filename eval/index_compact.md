# Pattern index (name · severity · trigger)

0. Boiling The Ocean [block] — A spec or plan lists three or more novel, unproven components (new runtime, new data model, new rendering surface, new protocol) that must all work before anything is usable.
1. The Big-Bang Relaunch [block] — A plan replaces an existing shipped surface in one release — 'v2 replaces v1', 'retire the old frame', 'cut over' — with no dual-run, opt-in, or staged migration.
2. Second-System Rewrite [block] — A proposal to rewrite a working module or surface from scratch, justified by cruft, where the new version is also scoped to fix known limitations of the old one.
3. Foundation Before First User [block] — A spec adds infrastructure — an index, cache, schema, consolidation pass, worker, centroid set, router — whose only named consumer is a feature not yet built or validated.
4. Technology Seeking A Job [block] — The spec leads with what the system can do ('we can embed / route / render / detect X') and the user's task appears only as a downstream illustration, or a hero feature has no named moment when someone would reach for it.
5. The Vanished Job [warn] — A roadmap item's rationale depends on a user behavior, environment, or third-party surface continuing to exist — 'when they're commuting', 'in their agent's window', 'while the CI runs', 'via partner X's API'.
6. Parity Roadmap [warn] — A requirement is justified by a competitor having it — 'X ships this', 'table stakes', 'we need parity', a feature-comparison matrix, or a decision that would change if that competitor disappeared.
7. Undifferentiated Price War [warn] — The plan competes on price, free-tier size, limits, discounting, or speed of copying a feature, in a market where a funded competitor can match the move immediately.
8. Growth Before Retention [block] — A plan proposes launch, marketing, headcount, or scale spend while retention, repeat usage, or activation is unmeasured, known-bad, or measured on a single cohort.
9. Org Chart Shipped To Users [warn] — A split, rename, or separation in the product mirrors an internal boundary (two teams, two repos, two services, two panes) and forces the user to move between surfaces to complete one task.
10. Sustaining-Only Roadmap [warn] — Every roadmap item deepens the product for existing or highest-paying users, and a cheaper, simpler, or lower-fidelity alternative in the market is dismissed as a toy or 'not our customer'.
11. Inflection Point Denial [warn] — A stated premise of the plan has visibly changed since it was written (a spec's corrections block, a superseded framing, a shipped assumption that is no longer true) and the plan continues incrementally against the old premise.
12. Refusing The Amputation [warn] — A v1 spec preserves every feature from a prototype or predecessor, and the scope-cut discussion produces deferrals ('phase 2', 'later slice', 'roadmap') rather than removals from the model.
13. Product Line Sprawl [warn] — The plan adds a new surface, product, SKU, CLI command, MCP tool, page, or entry point while existing ones are unfinished, unowned, or undocumented; a countable surface inventory grows.
14. Premature Automation [warn] — A spec automates onboarding, setup, matching, curation, routing, or support before that process has been performed by hand enough times to have written down the exception cases.
15. Job Mistaken For Demographic [note] — Requirements are segmented by who the user is (role, persona, seniority, company size, 'founders vs engineers') rather than by the situation and task at the moment of use.
16. Product Without Distribution [block] — A plan, sprint, or milestone is entirely product surface — polish, refactor, design review, quality bar — with no line item for how anyone discovers, installs, or is onboarded to it, or the distribution path is known to 404.
17. Chasing The Moving Baseline [warn] — In-flight work is rescoped to adopt a newly released model, framework, engine, API version, or internal abstraction before the current version has shipped to anyone.
18. Premature Platformization [block] — A spec introduces a protocol, plugin API, extension point, federation model, or abstraction justified by future third parties ('so others can build on it', 'generic enough for N cases') before one concrete case is in production.
19. One-Way Door Misread [block] — A diff or spec publishes something external parties will depend on: a public API endpoint, an MCP or CLI tool name, an event type or enum value, a URL scheme, a config key, an on-disk or wire format.
20. Two-Way Door Deliberated [note] — An easily reversible change — copy, layout, a default value, ordering, a flag's initial setting, a threshold — is escalated to a spec, a review cycle, or a founder decision.
21. The Metric That Moves Alone [warn] — A success criterion is a count that can increase while the underlying job goes unserved — events emitted, broadcasts sent, tool calls, DAU, sign-ups, page views — with no paired measure of whether the recipient acted on it.
22. Second-System Effect [block] — A spec or plan for a v2/next-gen version that lists features deferred from v1, or bundles a new data model + new UI + new extensibility layer in one release.
23. The Great Rewrite [block] — A prompt or issue proposing to "rewrite from scratch", "start clean", "greenfield it", or replace a working subsystem wholesale because the code is messy.
24. Man-Month Arithmetic [warn] — A plan responding to schedule slip by adding engineers, parallel agents, or extra workstreams to the same late deliverable.
25. Innovation Token Overdraft [warn] — A diff or spec that introduces a new datastore, language, queue, or orchestration layer — especially two or more in the same change — where an already-running component would do.
26. Distributed Monolith [warn] — A spec proposing a separate service, worker, repo, or deployable per entity/destination/integration, or a diff introducing an RPC boundary between two things that ship together.
27. Chesterton's Dead Code [block] — A diff that deletes or repurposes a feature flag, retry, guard clause, or branch labeled unused/deprecated/legacy without explaining what originally set it.
28. The Untested Restore [block] — A spec, runbook, or reply that mentions backups, snapshots, replicas, or disaster recovery as mitigation, with no restore drill or verification step.
29. The Never-Restarted Subsystem [warn] — A design involving a long-lived stateful service, cache, or index, where warm-up, rebuild, replay, or cold-start time is unstated or assumed fast.
30. Big-Bang Delivery [block] — A roadmap or plan whose milestones are all internal (design, build, integrate) with a single user-visible cutover at the end, and no shippable increment before it.
31. Launch Without Load [block] — A ship/launch date with no load or soak test in the plan, or a stated concurrency/throughput number that is an estimate rather than a measurement.
32. Pet Cluster Upgrade [warn] — An in-place upgrade, version bump, or migration of infrastructure described as legacy, hand-built, one-off, or "the original" — or config applied manually rather than from version control.
33. Global Blast Radius [block] — A change shipping to all users, machines, or tenants simultaneously — or a data/config/rules/prompt/template update path that bypasses the canary and staged-rollout used for code.
34. Reused Component, New Envelope [block] — A diff or plan that lifts an existing module, service, query, or library into a new scale, platform, region, or traffic profile described as reusing it "unchanged" or "as-is".
35. Interface Without A Contract [warn] — A new API field, event payload, or cross-team/cross-service boundary passing raw numbers, timestamps, identifiers, or strings with no shared type, unit, or validation at the boundary.
36. Automatic Failover Split-Brain [block] — A design adding automatic failover, leader election, multi-region writes, or a health-check-driven promotion — or any mention of a heartbeat timeout that decides who is authoritative.
37. Trivial Transitive Dependency [note] — A diff adding a package to package.json, go.mod, requirements.txt, or Cargo.toml — especially a small single-purpose one, or one arriving transitively rather than being chosen.
38. Complected Convenience [block] — A change adding implicit behavior to a shared path: string interpolation, template evaluation, auto-deserialization, dynamic dispatch on user data, or a "helpful" default that triggers without being requested.
39. Alert As The Fix [warn] — A proposed remediation that consists of logging a warning, emitting a metric, or adding a monitor — with no owner, threshold, or defined response — or a codebase with existing warnings nobody triages.
40. Preserving The Shape [warn] — A change explicitly scoped to avoid touching an existing schema, interface, migration, or retraining/re-certification cost — phrases like "without changing the existing", "to avoid a migration", "keep it backward compatible" driving the design rather than following it.
41. Control Plane Inside The Blast Radius [block] — A design where monitoring, deploy, auth, feature flags, or the rollback path runs on, resolves through, or authenticates against the same system it controls.
42. Guessing The Bottleneck [warn] — A diff or plan doing performance work — caching, batching, async, index, language/runtime swap — with no profile, benchmark, or production measurement cited, or a claim that something "should be faster".
43. Silent Mode Divergence [block] — A diff or spec adds a mode, toggle, view-state, or context in which the same control, keystroke, or input field produces different results — especially when the current mode is shown somewhere other than where the input happens.
44. Confirmation Instead Of Reversal [block] — A diff or spec guards a destructive, irreversible, or broadcast-to-others action with a confirmation dialog, checkbox, or type-to-confirm — and no undo window, recall, dry-run, or reversal path is specified.
45. Unlabeled Working Surface [warn] — Work touches an internal-only surface — CLI output, shell/SSH tooling, admin console, staging vs prod environment, log lines, migration scripts — and the change is justified as "internal, no design needed."
46. Signifier Erasure [warn] — A diff removes borders, background fills, underlines, or shadows from interactive elements, converts buttons to text/ghost buttons, or a spec asks to "make it cleaner / flatter / less chrome."
47. Metric As Taste Proxy [note] — A design disagreement is proposed to be settled by A/B test, click-through data, or "let's measure it" — particularly on typography, spacing, color, copy tone, or single-pixel values.
48. Redesign Riding A Rewrite [block] — A plan couples a visual/IA redesign with a platform migration, framework swap, schema change, or API rewrite in one release — or the rollback plan for a UI change is "revert the deploy" when the data model also changed.
49. Relearning Tax Ignored [warn] — A spec reorganizes navigation, moves an existing feature to a new location, renames a primary action, or changes the information architecture of a product that already has habituated daily users.
50. Craft On The Wrong Axis [warn] — A diff or spec invests heavy effort in something the user never sees, touches, or measures — an internal abstraction, a component's hidden tolerances, a custom build pipeline, a rendering engine — while the user-facing behavior is unchanged.
51. Stated Preference Trap [warn] — A spec justifies a feature with "users asked for it," a feature-request count, survey results, or a support-ticket theme — with no statement of what the addition costs in load time, screen density, or steps.
52. Discoverability Mistaken For Absence [note] — A ticket or spec proposes building a capability that may already exist somewhere in the product — "add a way to X," "users can't do Y" — without a check of whether X/Y already ships behind a menu, flag, or command.
53. Accessibility As Post-Ship Bug [block] — A spec or diff ships an interactive component with a11y noted as follow-up, or introduces custom interactive markup (div-as-button, custom modal, canvas UI, drag-and-drop) with no keyboard path, focus management, or accessible name.
54. Motion Without An Exit [warn] — A diff adds parallax, zoom transitions, autoplay, scroll-linked animation, or page transitions — and does not gate them behind prefers-reduced-motion or an equivalent user setting.
55. Prompt Inflation [warn] — A diff adds a confirmation dialog, permission prompt, toast, banner, badge, or notification to a flow that already has one — or a spec's answer to a risk is "warn the user."
56. Beautiful Prototype Bias [note] — A design is approved from a high-fidelity mock, Figma prototype, or rendered screenshot; or usability testing is run on a visually finished build without a low-fidelity or degraded-data comparison.
57. Native Control Replacement [warn] — A diff replaces a native element (select, date input, file input, scrollbar, checkbox, alert) with a custom component, or a design spec styles a control in a way only achievable by rebuilding it.
58. Control Swallowed By Screen [warn] — A spec relocates a frequent, urgent, or eyes-busy control into a screen, menu, submenu, command palette, or gesture — replacing a dedicated key, button, or always-visible affordance.
59. Curated Demo Data [warn] — A design, screenshot, or demo uses seeded, curated, or short sample data; or a spec has no defined empty state, long-string, stale-data, error, and high-volume case for the surface being built.
60. Assistant That Interrupts [warn] — A spec adds a proactive tip, coach mark, onboarding tour, suggestion popup, or AI assistant that appears without the user requesting it, based on inferred intent.
61. Metaphor Fusion [warn] — A spec describes the surface by joining categories with "and" ("it's a doc and a chat and a board"), unifies two existing product surfaces into one, or cannot state what the thing is in one sentence a non-user would repeat.
62. Friction Placed For Revenue [block] — A diff changes default selections, button placement/prominence, cancel-vs-confirm ordering, or opt-out wording in a purchase, subscription, consent, sharing, or account-deletion flow in a way that favors the business.
63. Error Text From Inside [warn] — A diff adds or changes user-visible error, empty, or status copy that names an internal condition (state names, error codes, subsystem names, exception text) instead of what failed plus one concrete action the user can take.
64. One Shell, Two Inputs [warn] — A spec targets one UI across incompatible input modes or form factors — touch and mouse, mobile and desktop, TV and handheld — or introduces hover-dependent or edge-gesture affordances in a surface that must also work with the other input.
65. Distribution As An Afterthought [block] — A roadmap, spec, or milestone list where every item is a product capability and no item names a specific acquisition channel, or a plan that says marketing/launch/GTM happens "after v1".
66. Channel-Price Mismatch [block] — A GTM plan or budget line proposing Google/Meta/LinkedIn/Reddit ads, sponsorships, or outbound SDRs without stating ARPU, gross margin, and a payback period in months.
67. CAC Buried In COGS [block] — A growth dashboard, OKR, or investor update whose headline metric is signups, downloads, trials, or new customers, with no cohort retention curve or LTV:CAC ratio alongside it.
68. Negative Unit Economics As Growth [block] — A pricing proposal with unlimited/all-you-can-eat framing, a price below the per-user infrastructure or fulfillment cost, or copy promising to monetize later via ads, data, or upsell.
69. Retroactive Value-Metric Change [block] — A pricing change that alters the billing unit (seats→usage, revenue→installs, flat→metered), reprices existing contracts, or applies to activity that already happened.
70. Segment-Blind PMF Survey [warn] — A proposal to run the 40% test, NPS, or a satisfaction survey across the full user list, or a stated PMF/NPS number reported as one figure with no segment breakdown.
71. Premature Scaling [block] — A plan that adds headcount, geographies, warehouses, regions, or provisioned infrastructure capacity on a schedule rather than in response to a measured demand signal; "build it so it scales to N" before N/100 exists.
72. Funding As Distribution [warn] — A launch plan whose top-of-funnel is press coverage, a funding announcement, an influencer/analyst push, or a Product Hunt / HN / Show HN day, with no channel that keeps producing users on day 30.
73. Paid Launch Without A Loop [block] — A GTM plan with a large paid media budget, a launch-day ad buy, or a campaign brief, where no line item describes an in-product mechanism that generates the next user.
74. Built On Rented Land [warn] — A growth mechanism that depends on another company's API, social graph, app-store placement, feed distribution, marketplace listing, extension store, or OAuth integration as the primary source of new users.
75. Feature Parity Positioning [warn] — A positioning doc, landing page, or spec that frames the product as "X but better/faster/cheaper", or leads with a feature-comparison table against a named incumbent.
76. Positioning To The Wrong Frame [warn] — Copy or a spec that names a broad established category ("CRM", "project management", "observability", "coordination layer") without naming the specific buyer and the specific alternative they'd otherwise use.
77. No Beachhead [warn] — TAM-driven sizing, "for any team / any company / everyone who...", or a launch plan listing three or more personas with no ranking of which one ships first.
78. Cold Start Ignored [block] — A spec for a feed, map, marketplace, roster, leaderboard, directory, team view, or any social surface, with no stated plan for what a first user or solo user sees.
79. Skipping The Unscalable [warn] — A plan to build self-serve signup, an onboarding wizard, an email drip, an in-app tour, or a help center before roughly ten users have been onboarded by a founder in person.
80. Free Tier With No Wall [warn] — A spec adding a free plan, free tier, or open beta whose limits are storage, seats-of-one, retention window, or time, rather than the specific capability a committed user cannot work without; also any "free forever" framing.
81. Hype Ahead Of Usability [warn] — A launch plan gated by waitlist or invite codes, or a demo script/video longer than about two minutes that requires narration to make the product legible.
82. Seat Pricing Punishes Adoption [warn] — A pricing page or spec charging per seat, per user, or per member for a product whose core value requires a whole team, or charging full price for read-only/viewer/observer roles.
83. Single Channel Concentration [warn] — A growth model that extrapolates the current dominant channel's conversion rate forward, or a plan where one channel already supplies most users and no second-channel experiment is funded and dated.
84. Referral On A Leaky Bucket [warn] — A spec adding a referral program, invite bonus, share incentive, or affiliate scheme when D30 retention is unknown, unstated, or declining, or where the reward is unrelated to the product's core value.
85. Piggyback Channel Ignored [note] — A GTM plan whose channel list contains only owned surfaces (own blog, own newsletter, own social account, own docs site) and names no existing venue, marketplace, forum, or community where the target users already gather.
86. The Inside-View Estimate [warn] — A plan, spec, or roadmap states a duration, ship date, or phase count derived by listing the work, with no reference to how long a comparable past effort actually took.
87. Fixed Date Beats Evidence [block] — An immovable external date (launch event, conference demo, investor meeting, contract deadline) is stated, and someone with direct prior experience of the same work says the schedule is short.
88. Silent Room Consensus [warn] — A prompt or doc asserts "the team is aligned", "no objections were raised", or "we all agreed" without naming a specific person who argued the other side and what they said.
89. Preference-First Framing [warn] — A request to review, sign off on, or implement an approach whose author has already stated a preferred outcome, or a message shaped as "here's what we're doing — thoughts?"
90. The Deck Instead Of The Memo [note] — A plan or spec arrives as a feature list, bullet outline, table, or phase grid with no prose section stating the problem, the constraints, and what evidence would falsify the approach.
91. Commit Without Disagreeing [note] — A decision is recorded with unanimous support and then reopened, slow-walked, or partially implemented; or a teammate agrees to a plan in one message and questions its premise in a later one.
92. Numbers Nobody Measured [block] — A spec, README, or marketing line quotes a reliability, latency, uptime, accuracy, or coverage figure without naming the measurement that produced it.
93. Root Cause Singular [warn] — An incident writeup, postmortem, or bug analysis names exactly one root cause and one code-level fix, with no finding about how the defect passed review or shipped.
94. The Metric Becomes The Job [block] — A spec, OKR, or plan ties compensation, ranking, or a pass/fail gate to a single countable output (accounts, PRs merged, tickets closed, coverage percent, broadcasts sent).
95. Compliance As Friction [block] — A prompt or diff proposes bypassing, auto-satisfying, or faking a legal, licensing, security-review, audit-log, or approval requirement on the grounds that the requirement is overhead.
96. Statistics Against Trust [block] — A response to a user-reported bug, data-loss report, or wrong-output complaint leads with how rare the condition is, or proposes closing it as won't-fix on frequency grounds.
97. The Approval Bottleneck [warn] — A process or spec routes every instance of a recurring decision (hires, merges, deploys, copy changes, place bindings) through one named approver, with no delegation rule or bypass condition.
98. Announcing The Successor [warn] — Customer-facing copy, changelog, docs, or a public roadmap describes a currently shipping product, framing, or API as deprecated, weak, or superseded before its replacement is available.
99. Sunk Identity [warn] — A decision or spec is defended by how much has already been built, how long it took, or by identity language ("we're a X company", "this is our thesis"), rather than by the option's forward value.
100. Exit Reason Assumed [note] — An explanation of attrition, churn, drop-off, or non-adoption asserts a cause (price, speed, missing feature) without citing anything the departed users or teammates actually said.
101. Adding People To A Late Thing [warn] — A slipping deliverable is answered by assigning more engineers, more parallel agents, or more concurrent sessions to the same component or file set, rather than by cutting scope.
102. The Famous Forecaster [note] — A claim about the future (adoption, competitor behavior, market timing, "users will want X") is backed by seniority, conviction, or a cited authority rather than by a dated, falsifiable statement someone will check.
103. One-Way Door, Casual [warn] — A decision that forecloses a future option (a partnership declined, a public API committed, a naming/positioning lock, a data model that cannot be migrated) is being made in the same pass as routine work, with no note distinguishing it.
104. Wartime Frame In Peacetime [warn] — An existential condition is stated (runway, a competitor shipping the core feature, a broken primary flow, zero users) and the proposed response is a broad multi-track plan, a process change, or a round of alignment.
105. Cofounder Equity Without Vesting [block] — A cofounder split, advisor grant, contractor equity arrangement, or early-employee offer is described with a percentage but no vesting schedule, cliff, or repurchase right.
106. The Concealed Constraint [block] — A design or documentation decision is justified by preserving a commercial or compatibility commitment ("no retraining", "no migration", "no API break", "don't scare the customer") rather than by the requirement itself — especially when it removes a mechanism from docs while keeping it in code.
