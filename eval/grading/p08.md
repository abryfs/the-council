# p08

**Prompt the founder typed:**
> why is this regex not matching? `^[\w.-]+@[\w-]+\.[a-z]{2,}$` — it fails on foo+bar@sub.example.co.uk and I don't see why

_Context: Debugging a validation function that keeps rejecting valid input_

For EACH set below, judge EACH pattern: is it genuinely relevant to this specific prompt — would surfacing it change or improve how an agent handles this request? Be strict. A pattern that is merely topically adjacent is NOT relevant.


## Set A

- **Interface Without A Contract** — When two components exchange bare numbers or strings, the meaning (unit, timezone, encoding, ID namespace) lives only in each side's head. Nothing at the boundary can detect disagreement, so the mismatch propagates as plausible-looking data instead of an error. TRIGGER: A new API field, event payload, or cross-team/cross-service boundary passing raw numbers, timestamps, identifiers, or strings with no shared type, unit, or validation at the boundary.
- **Curated Demo Data** — Designs validated on hand-picked content encode assumptions about length, density, freshness, and correctness that real data violates on day one; the demo proves the layout, not the product, and the gap surfaces publicly at launch scale. TRIGGER: A design, screenshot, or demo uses seeded, curated, or short sample data; or a spec has no defined empty state, long-string, stale-data, error, and high-volume case for the surface being built.
- **Error Text From Inside** — A message written from the system's state names a condition the user has no model for and no action attached to; it is technically accurate and operationally useless, so the user's only remaining move is to ask a human or abandon the task. TRIGGER: A diff adds or changes user-visible error, empty, or status copy that names an internal condition (state names, error codes, subsystem names, exception text) instead of what failed plus one concrete action the user can take.
- **Chesterton's Dead Code** — Code that appears unused is often reachable through a path nobody has in mind — an old flag, a stale server, a legacy client — so removing the guard while leaving the code, or reusing its switch for a new meaning, arms a landmine that only fires under partial deployment. TRIGGER: A diff that deletes or repurposes a feature flag, retry, guard clause, or branch labeled unused/deprecated/legacy without explaining what originally set it.
- **Complected Convenience** — Braiding an extra capability into a general-purpose path means every caller of that path silently gains the capability, including callers handling attacker-controlled input. The convenience is opt-out by omission rather than opt-in by intent. TRIGGER: A change adding implicit behavior to a shared path: string interpolation, template evaluation, auto-deserialization, dynamic dispatch on user data, or a "helpful" default that triggers without being requested.
- **Root Cause Singular** — Five-whys terminates at the first cause that is both technical and fixable, because that node is where the search stops feeling productive. The organizational conditions that let the technical fault reach production are upstream of that stopping point, so they survive the fix and reproduce it. TRIGGER: An incident writeup, postmortem, or bug analysis names exactly one root cause and one code-level fix, with no finding about how the defect passed review or shipped.
- **Statistics Against Trust** — Answering a reported defect with its probability treats the user's problem as frequency when the actual damage is to the belief that the product's outputs can be relied on without checking. The probability argument is usually correct and always escalates, because it tells the reporter their experience does not count. TRIGGER: A response to a user-reported bug, data-loss report, or wrong-output complaint leads with how rare the condition is, or proposes closing it as won't-fix on frequency grounds.
- **Numbers Nobody Measured** — A quantitative claim with no measurement behind it still functions as one downstream — it gets cited, budgeted against, and used to close arguments — because the number's format carries authority its provenance does not. Organizations generate these numbers where the desired answer is known and the measurement is expensive. TRIGGER: A spec, README, or marketing line quotes a reliability, latency, uptime, accuracy, or coverage figure without naming the measurement that produced it.
- **Native Control Replacement** — Platform controls carry years of accumulated behavior — keyboard, IME, screen readers, touch targets, zoom, autofill — that is invisible in the visual spec; a custom reimplementation reproduces the appearance and silently drops the behavior, and the loss shows up only for users you are not. TRIGGER: A diff replaces a native element (select, date input, file input, scrollbar, checkbox, alert) with a custom component, or a design spec styles a control in a way only achievable by rebuilding it.
- **Trivial Transitive Dependency** — A dependency's risk is set by the reliability of its publishing and maintenance, not by its size, and transitive pulls mean the risky package is one nobody chose. Eleven lines of code can carry the same availability and supply-chain exposure as eleven thousand. TRIGGER: A diff adding a package to package.json, go.mod, requirements.txt, or Cargo.toml — especially a small single-purpose one, or one arriving transitively rather than being chosen.
- **Guessing The Bottleneck** — Intuition about performance is trained on the code you read, while cost lives in behavior you cannot see — allocation, cache misses, scheduler and GC intervals, tail latency. Optimizing before profiling spends effort on the wrong axis and hides the real cause behind a changed baseline. TRIGGER: A diff or plan doing performance work — caching, batching, async, index, language/runtime swap — with no profile, benchmark, or production measurement cited, or a claim that something "should be faster".
- **Reused Component, New Envelope** — A component's correctness depends on the operating envelope it was validated in — value ranges, clock rates, load profile. Reuse carries the code but not the envelope, and the assumption that made it safe becomes silently false. TRIGGER: A diff or plan that lifts an existing module, service, query, or library into a new scale, platform, region, or traffic profile described as reusing it "unchanged" or "as-is".
- **Preserving The Shape** — When a change is bolted onto an existing structure specifically to avoid disturbing it — because touching it would trigger a migration, recertification, or retraining cost — the new behavior inherits constraints it was never designed for, and the reason to avoid them becomes a reason not to fix them. TRIGGER: A change explicitly scoped to avoid touching an existing schema, interface, migration, or retraining/re-certification cost — phrases like "without changing the existing", "to avoid a migration", "keep it backward compatible" driving the design rather than following it.
- **Accessibility As Post-Ship Bug** — Accessibility is decided by structure — semantics, focus order, names, contrast — which is fixed at the moment the component is built; deferring it converts a design constraint into a rewrite, and in many jurisdictions into legal exposure that no backlog priority can defer. TRIGGER: A spec or diff ships an interactive component with a11y noted as follow-up, or introduces custom interactive markup (div-as-button, custom modal, canvas UI, drag-and-drop) with no keyboard path, focus management, or accessible name.
- **Two-Way Door Deliberated** — Applying heavyweight process to a reversible decision costs more than being wrong would have, and the delay itself removes the cheapest source of information — shipping it and watching. Organizations default to the heavy process for everything because the process was designed around the rare irreversible case. TRIGGER: An easily reversible change — copy, layout, a default value, ordering, a flag's initial setting, a threshold — is escalated to a spec, a review cycle, or a founder decision.

## Set B

- **Boiling The Ocean** — When v1 requires three or more unproven components to all work at once, the probability of shipping is the product of each part's odds, and no single part can be validated until the others exist. Learning is deferred until the whole thing is done, which is exactly when it is most expensive to be wrong. TRIGGER: A spec or plan lists three or more novel, unproven components (new runtime, new data model, new rendering surface, new protocol) that must all work before anything is usable.
- **Big-Bang Delivery** — When integration is scheduled once at the end, every incorrect assumption compounds silently for the whole project and all of them surface simultaneously, at the moment there is no budget left to act on them. Nothing is falsified until it is too late to be cheap. TRIGGER: A roadmap or plan whose milestones are all internal (design, build, integrate) with a single user-visible cutover at the end, and no shippable increment before it.
- **Referral On A Leaky Bucket** — Referral loops are multipliers on retention, not substitutes for it: each invited user only produces further invites if the product held the inviter long enough to make inviting worthwhile. Bolted onto a product with poor retention, a referral program simply spends incentive budget accelerating churn through the funnel. TRIGGER: A spec adding a referral program, invite bonus, share incentive, or affiliate scheme when D30 retention is unknown, unstated, or declining, or where the reward is unrelated to the product's core value.
- **Premature Automation** — Automating a process before doing it manually encodes a guess about the rules into code, and the code then prevents you from observing the exceptions that would have taught you the real rules. Manual work at small N is not a stopgap, it is the only instrument that reads the requirement. TRIGGER: A spec automates onboarding, setup, matching, curation, routing, or support before that process has been performed by hand enough times to have written down the exception cases.
- **Root Cause Singular** — Five-whys terminates at the first cause that is both technical and fixable, because that node is where the search stops feeling productive. The organizational conditions that let the technical fault reach production are upstream of that stopping point, so they survive the fix and reproduce it. TRIGGER: An incident writeup, postmortem, or bug analysis names exactly one root cause and one code-level fix, with no finding about how the defect passed review or shipped.
- **The Metric That Moves Alone** — A proxy metric that can rise without the underlying job being served will be optimized directly, because it is the thing that is measured and reported; the product then drifts toward whatever produces the number, and the gap between metric and job widens fastest exactly when the metric looks best. TRIGGER: A success criterion is a count that can increase while the underlying job goes unserved — events emitted, broadcasts sent, tool calls, DAU, sign-ups, page views — with no paired measure of whether the recipient acted on it.
- **Man-Month Arithmetic** — Adding people to a late project adds onboarding cost and communication paths (n²) before it adds throughput, and the work that is late is usually serially dependent, so the added capacity cannot be applied to the critical path. TRIGGER: A plan responding to schedule slip by adding engineers, parallel agents, or extra workstreams to the same late deliverable.
- **Skipping The Unscalable** — Automating the first-user experience before doing it by hand encodes your guesses about what users need into software, and the automation then hides the disconfirming evidence. Manual onboarding is not inefficiency; it is the only instrument fine-grained enough to find the problem that the metrics summarize away. TRIGGER: A plan to build self-serve signup, an onboarding wizard, an email drip, an in-app tour, or a help center before roughly ten users have been onboarded by a founder in person.
- **Refusing The Amputation** — Deferring a feature to 'phase 2' keeps it in the architecture — its data model, its surface area, its coupling — so the v1 carries the full complexity cost while delivering none of the value. Deletion is the only scope cut that actually reduces work; deferral is bookkeeping. TRIGGER: A v1 spec preserves every feature from a prototype or predecessor, and the scope-cut discussion produces deferrals ('phase 2', 'later slice', 'roadmap') rather than removals from the model.
- **Premature Platformization** — A protocol, plugin API, or generality invented before one concrete use is in production is designed against imagined consumers, so it optimizes for flexibility no one needs while missing the constraint the first real user would have imposed. It also raises the cost of every subsequent change, because generality is what you promise not to break. TRIGGER: A spec introduces a protocol, plugin API, extension point, federation model, or abstraction justified by future third parties ('so others can build on it', 'generic enough for N cases') before one concrete case is in production.
- **Redesign Riding A Rewrite** — Shipping a new surface on top of a new backend at once destroys attribution and rollback simultaneously: you cannot tell whether users hate the design or the bugs, and you cannot revert the design because the old one no longer has a system underneath it. TRIGGER: A plan couples a visual/IA redesign with a platform migration, framework swap, schema change, or API rewrite in one release — or the rollback plan for a UI change is "revert the deploy" when the data model also changed.
- **Premature Scaling** — Capacity built ahead of demand converts fixed costs into a deadline: the burn rate now sets how long you have to find the demand, rather than the demand setting how much you build. Because the capacity is sunk, the team also loses the option to change the shape of the business when the early signal comes back wrong. TRIGGER: A plan that adds headcount, geographies, warehouses, regions, or provisioned infrastructure capacity on a schedule rather than in response to a measured demand signal; "build it so it scales to N" before N/100 exists.
- **Pet Cluster Upgrade** — Infrastructure configured by hand and not committed anywhere has no record of what depends on what, so an upgrade that changes an implicit contract (a label, a default, a deprecated field) breaks something nobody can trace back. Recovery becomes archaeology under time pressure. TRIGGER: An in-place upgrade, version bump, or migration of infrastructure described as legacy, hand-built, one-off, or "the original" — or config applied manually rather than from version control.
- **Job Mistaken For Demographic** — Segmenting by who the user is produces feature requests that correlate with the segment but explain nothing causal, so improvements aimed at the persona miss the situation that actually triggered the purchase. Two people in the same demographic hire the product for opposite jobs, and averaging them produces a product for neither. TRIGGER: Requirements are segmented by who the user is (role, persona, seniority, company size, 'founders vs engineers') rather than by the situation and task at the moment of use.
- **Product Line Sprawl** — Each additional surface, SKU, or entry point consumes maintenance, documentation, support, and decision bandwidth permanently, while the marginal one is almost always worse than the median — so average quality falls monotonically as count rises, and the team's best people are spread across things no one would start today. TRIGGER: The plan adds a new surface, product, SKU, CLI command, MCP tool, page, or entry point while existing ones are unfinished, unowned, or undocumented; a countable surface inventory grows.

## Set C

- **Product Without Distribution** — Product quality and reach are independent variables, and quality has no mechanism to produce reach on its own — a plan composed entirely of product work therefore converges on an excellent thing nobody can find, while the burn clock runs at the same rate either way. TRIGGER: A plan, sprint, or milestone is entirely product surface — polish, refactor, design review, quality bar — with no line item for how anyone discovers, installs, or is onboarded to it, or the distribution path is known to 404.
- **Premature Automation** — Automating a process before doing it manually encodes a guess about the rules into code, and the code then prevents you from observing the exceptions that would have taught you the real rules. Manual work at small N is not a stopgap, it is the only instrument that reads the requirement. TRIGGER: A spec automates onboarding, setup, matching, curation, routing, or support before that process has been performed by hand enough times to have written down the exception cases.
- **No Beachhead** — A message aimed at everyone is specific to no one, so it fails the only test that matters early: can one user explain it to the next user in a sentence. Without a defined first customer, price, channel, and objection-handling all become guesses, and there is no dense population in which word of mouth can propagate. TRIGGER: TAM-driven sizing, "for any team / any company / everyone who...", or a launch plan listing three or more personas with no ranking of which one ships first.
- **The Inside-View Estimate** — An estimate built by decomposing the specific task counts only the steps you can currently see, and the steps you cannot see are exactly the ones that consume the schedule. Decomposition feels more rigorous than a base rate, so it displaces the base rate rather than being checked against it. TRIGGER: A plan, spec, or roadmap states a duration, ship date, or phase count derived by listing the work, with no reference to how long a comparable past effort actually took.
- **Control Swallowed By Screen** — A screen control demands visual attention and offers no tactile confirmation, so moving a frequent or eyes-busy action into a menu converts a sub-second muscle-memory operation into a look-navigate-aim-verify loop. The cost is invisible in a demo where the user is already looking at the screen. TRIGGER: A spec relocates a frequent, urgent, or eyes-busy control into a screen, menu, submenu, command palette, or gesture — replacing a dedicated key, button, or always-visible affordance.
- **Parity Roadmap** — Building a feature because a competitor has it imports their strategy and their constraints without their distribution, and a checklist match gives an existing user of the incumbent no reason to switch — matching is by definition not a differentiator. It also consumes the scarce build capacity that would have produced one. TRIGGER: A requirement is justified by a competitor having it — 'X ships this', 'table stakes', 'we need parity', a feature-comparison matrix, or a decision that would change if that competitor disappeared.
- **Feature Parity Positioning** — Positioning your product as a better version of an incumbent asks the customer to compare on the incumbent's chosen axes, where the incumbent's scale wins by construction, and it gives no one a reason to bear switching cost. Parity is also unbounded work: matching the feature list is a treadmill the incumbent sets the speed of. TRIGGER: A positioning doc, landing page, or spec that frames the product as "X but better/faster/cheaper", or leads with a feature-comparison table against a named incumbent.
- **Guessing The Bottleneck** — Intuition about performance is trained on the code you read, while cost lives in behavior you cannot see — allocation, cache misses, scheduler and GC intervals, tail latency. Optimizing before profiling spends effort on the wrong axis and hides the real cause behind a changed baseline. TRIGGER: A diff or plan doing performance work — caching, batching, async, index, language/runtime swap — with no profile, benchmark, or production measurement cited, or a claim that something "should be faster".
- **Distribution As An Afterthought** — Product work has a legible feedback loop (ship, see it work) and distribution does not, so engineering-led teams spend the entire runway on the loop that feels productive and reach the market with no channel built. By the time distribution becomes urgent, the money that would have funded channel experiments is already spent on the product. TRIGGER: A roadmap, spec, or milestone list where every item is a product capability and no item names a specific acquisition channel, or a plan that says marketing/launch/GTM happens "after v1".
- **Silent Mode Divergence** — When one control's meaning depends on a mode the user cannot see at the moment of input, the interface accepts a correct-looking action and executes a different one; the operator's mental model and the machine's state diverge with no feedback to reconcile them. TRIGGER: A diff or spec adds a mode, toggle, view-state, or context in which the same control, keystroke, or input field produces different results — especially when the current mode is shown somewhere other than where the input happens.
- **Boiling The Ocean** — When v1 requires three or more unproven components to all work at once, the probability of shipping is the product of each part's odds, and no single part can be validated until the others exist. Learning is deferred until the whole thing is done, which is exactly when it is most expensive to be wrong. TRIGGER: A spec or plan lists three or more novel, unproven components (new runtime, new data model, new rendering surface, new protocol) that must all work before anything is usable.
- **The Big-Bang Relaunch** — Replacing a shipped surface wholesale in one release couples a hundred independent bets into a single irreversible event, so you cannot tell which change caused the loss, and existing users pay the full re-learning cost on a day they did not choose. Habitual users are the ones who notice most, and they are the ones you can least afford to lose. TRIGGER: A plan replaces an existing shipped surface in one release — 'v2 replaces v1', 'retire the old frame', 'cut over' — with no dual-run, opt-in, or staged migration.
- **Second-System Rewrite** — A rewrite is scoped against the accumulated wishlist of everything the old system got wrong, so the new system is strictly larger than the one that already took years. Meanwhile the old system keeps shipping nothing, and the rewrite's real cost is the undocumented edge cases embedded in the code being discarded. TRIGGER: A proposal to rewrite a working module or surface from scratch, justified by cruft, where the new version is also scoped to fix known limitations of the old one.
- **Foundation Before First User** — Infrastructure built for a feature that does not exist has no consumer to falsify its design, so its interface is derived from imagination and calcifies before contact. The dependent feature then inherits constraints from a substrate that was never tested against the real requirement. TRIGGER: A spec adds infrastructure — an index, cache, schema, consolidation pass, worker, centroid set, router — whose only named consumer is a feature not yet built or validated.
- **Technology Seeking A Job** — When the differentiator is stated as a capability rather than a task someone was already trying to accomplish, the feature has no natural moment of use, so adoption requires teaching a new behavior instead of intercepting an existing one. Impressive capability and unused capability are fully compatible. TRIGGER: The spec leads with what the system can do ('we can embed / route / render / detect X') and the user's task appears only as a downstream illustration, or a hero feature has no named moment when someone would reach for it.
