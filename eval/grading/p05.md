# p05

**Prompt the founder typed:**
> My cofounder wants to rewrite the backend in Rust. His argument is the Node service is already showing latency problems under load and we'll have to do it eventually anyway. I think it's a 6 week detour. Help me think about this — and if I'm wrong I want to know.

_Context: Cofounder disagreement about the backend stack, mid-week_

For EACH set below, judge EACH pattern: is it genuinely relevant to this specific prompt — would surfacing it change or improve how an agent handles this request? Be strict. A pattern that is merely topically adjacent is NOT relevant.


## Set A

- **Stated Preference Trap** — Users accurately report what they want and cannot report what it costs, because the cost (latency, density, decision load) is a property of the system, not of the wish. Delivering the requested thing literally can move the metric the wrong way. TRIGGER: A spec justifies a feature with "users asked for it," a feature-request count, survey results, or a support-ticket theme — with no statement of what the addition costs in load time, screen density, or steps.
- **Second-System Rewrite** — A rewrite is scoped against the accumulated wishlist of everything the old system got wrong, so the new system is strictly larger than the one that already took years. Meanwhile the old system keeps shipping nothing, and the rewrite's real cost is the undocumented edge cases embedded in the code being discarded. TRIGGER: A proposal to rewrite a working module or surface from scratch, justified by cruft, where the new version is also scoped to fix known limitations of the old one.
- **Redesign Riding A Rewrite** — Shipping a new surface on top of a new backend at once destroys attribution and rollback simultaneously: you cannot tell whether users hate the design or the bugs, and you cannot revert the design because the old one no longer has a system underneath it. TRIGGER: A plan couples a visual/IA redesign with a platform migration, framework swap, schema change, or API rewrite in one release — or the rollback plan for a UI change is "revert the deploy" when the data model also changed.
- **Distributed Monolith** — Splitting a codebase into services that share a release cadence and shared libraries converts in-process function calls into network calls without decoupling deploys, so you pay partial-failure, latency, and operational cost while keeping every coupling you had. TRIGGER: A spec proposing a separate service, worker, repo, or deployable per entity/destination/integration, or a diff introducing an RPC boundary between two things that ship together.
- **Reused Component, New Envelope** — A component's correctness depends on the operating envelope it was validated in — value ranges, clock rates, load profile. Reuse carries the code but not the envelope, and the assumption that made it safe becomes silently false. TRIGGER: A diff or plan that lifts an existing module, service, query, or library into a new scale, platform, region, or traffic profile described as reusing it "unchanged" or "as-is".
- **Cofounder Equity Without Vesting** — Equity granted without vesting or a cliff prices a contribution before it has happened, and the grant survives the contributor's departure, disagreement, or non-performance. The dispute surfaces at the financing or acquisition that makes the equity worth litigating, which is the worst possible moment to have it. TRIGGER: A cofounder split, advisor grant, contractor equity arrangement, or early-employee offer is described with a percentage but no vesting schedule, cliff, or repurchase right.
- **Launch Without Load** — Capacity assumptions that are never measured are wrong in the unsafe direction, because designers estimate from the intended usage rather than the arrival pattern. Load appears as a step function at launch, not a ramp, so the first real test is also the first outage. TRIGGER: A ship/launch date with no load or soak test in the plan, or a stated concurrency/throughput number that is an estimate rather than a measurement.
- **The Famous Forecaster** — Confidence and reputation are produced by a different process than accuracy, and in public settings they are rewarded more, so the loudest forecast is systematically the least hedged. Without a resolution date and a scoring rule, no forecast ever gets marked wrong, and the calibration signal never reaches anyone. TRIGGER: A claim about the future (adoption, competitor behavior, market timing, "users will want X") is backed by seniority, conviction, or a cited authority rather than by a dated, falsifiable statement someone will check.
- **Skipping The Unscalable** — Automating the first-user experience before doing it by hand encodes your guesses about what users need into software, and the automation then hides the disconfirming evidence. Manual onboarding is not inefficiency; it is the only instrument fine-grained enough to find the problem that the metrics summarize away. TRIGGER: A plan to build self-serve signup, an onboarding wizard, an email drip, an in-app tour, or a help center before roughly ten users have been onboarded by a founder in person.
- **Statistics Against Trust** — Answering a reported defect with its probability treats the user's problem as frequency when the actual damage is to the belief that the product's outputs can be relied on without checking. The probability argument is usually correct and always escalates, because it tells the reporter their experience does not count. TRIGGER: A response to a user-reported bug, data-loss report, or wrong-output complaint leads with how rare the condition is, or proposes closing it as won't-fix on frequency grounds.
- **The Great Rewrite** — A rewrite discards the accumulated bug fixes encoded in the old code — each ugly branch is a defect someone found in production — while the old system keeps needing maintenance, so the team pays for two systems and ships neither. TRIGGER: A prompt or issue proposing to "rewrite from scratch", "start clean", "greenfield it", or replace a working subsystem wholesale because the code is messy.
- **Innovation Token Overdraft** — Every unfamiliar technology carries unknown failure modes that only surface under production load, and each one consumes the same scarce resource: engineer attention during incidents. Spending several at once means every outage has multiple novel suspects and no one has intuition about any of them. TRIGGER: A diff or spec that introduces a new datastore, language, queue, or orchestration layer — especially two or more in the same change — where an already-running component would do.
- **The Deck Instead Of The Memo** — Bullets let a proposal omit the connective tissue — the constraint, the alternative rejected, the thing that would make this wrong — because a bullet has no grammar that requires them. The gaps are invisible to the reader and often to the author, who mistakes the deck's completeness for the argument's. TRIGGER: A plan or spec arrives as a feature list, bullet outline, table, or phase grid with no prose section stating the problem, the constraints, and what evidence would falsify the approach.
- **Numbers Nobody Measured** — A quantitative claim with no measurement behind it still functions as one downstream — it gets cited, budgeted against, and used to close arguments — because the number's format carries authority its provenance does not. Organizations generate these numbers where the desired answer is known and the measurement is expensive. TRIGGER: A spec, README, or marketing line quotes a reliability, latency, uptime, accuracy, or coverage figure without naming the measurement that produced it.
- **The Never-Restarted Subsystem** — Long-lived services grow past the scale their cold-start path was designed for, and because that path never runs, the regression is invisible until the day you need it. Recovery time then becomes an unknown discovered during the outage. TRIGGER: A design involving a long-lived stateful service, cache, or index, where warm-up, rebuild, replay, or cold-start time is unstated or assumed fast.

## Set B

- **The Great Rewrite** — A rewrite discards the accumulated bug fixes encoded in the old code — each ugly branch is a defect someone found in production — while the old system keeps needing maintenance, so the team pays for two systems and ships neither. TRIGGER: A prompt or issue proposing to "rewrite from scratch", "start clean", "greenfield it", or replace a working subsystem wholesale because the code is messy.
- **Guessing The Bottleneck** — Intuition about performance is trained on the code you read, while cost lives in behavior you cannot see — allocation, cache misses, scheduler and GC intervals, tail latency. Optimizing before profiling spends effort on the wrong axis and hides the real cause behind a changed baseline. TRIGGER: A diff or plan doing performance work — caching, batching, async, index, language/runtime swap — with no profile, benchmark, or production measurement cited, or a claim that something "should be faster".
- **Innovation Token Overdraft** — Every unfamiliar technology carries unknown failure modes that only surface under production load, and each one consumes the same scarce resource: engineer attention during incidents. Spending several at once means every outage has multiple novel suspects and no one has intuition about any of them. - **Numbers Nobody Measured** — A quantitative claim with no measurement behind it still functions as one downstream — it gets cited, budgeted against, and used to close arguments — because the number's format carries authority its provenance does not. TRIGGER: A spec, README, or marketing line quotes a reliability, latency, uptime, accuracy, or coverage figure without naming the measurement that produced it.
- **The Inside-View Estimate** — An estimate built by decomposing the specific task counts only the steps you can currently see, and the steps you cannot see are exactly the ones that consume the schedule. Decomposition feels more rigorous than a base rate, so it displaces the base rate rather than being checked against it. TRIGGER: A plan, spec, or roadmap states a duration, ship date, or phase count derived by listing the work, with no reference to how long a comparable past effort actually took.
- **The Famous Forecaster** — Confidence and reputation are produced by a different process than accuracy, and in public settings they are rewarded more, so the loudest forecast is systematically the least hedged. Without a resolution date and a scoring rule, no forecast ever gets marked wrong, and the calibration signal never reaches anyone. TRIGGER: A claim about the future (adoption, competitor behavior, market timing, "users will want X") is backed by seniority, conviction, or a cited authority rather than by a dated, falsifiable statement someone will check.
- **Preference-First Framing** — When the decision-maker states their conclusion before soliciting input, every subsequent contribution is scored by the contributor against the cost of contradicting them, not against the evidence. Input arrives, so the process looks consultative, but it has been filtered to what survives disagreement with the boss. TRIGGER: A request to review, sign off on, or implement an approach whose author has already stated a preferred outcome, or a message shaped as "here's what we're doing — thoughts?"
- **Premature Scaling** — Capacity built ahead of demand converts fixed costs into a deadline: the burn rate now sets how long you have to find the demand, rather than the demand setting how much you build. Because the capacity is sunk, the team also loses the option to change the shape of the business when the early signal comes back wrong. TRIGGER: A plan that adds headcount, geographies, warehouses, regions, or provisioned infrastructure capacity on a schedule rather than in response to a measured demand signal; "build it so it scales to N" before N/100 exists.
- **Commit Without Disagreeing** — An unrecorded disagreement does not disappear; it re-emerges as slow execution, quiet re-litigation, and a preserved right to say "I never liked this" when the result is bad. Writing the disagreement down before committing is what converts a private hedge into a shared bet. TRIGGER: A decision is recorded with unanimous support and then reopened, slow-walked, or partially implemented; or a teammate agrees to a plan in one message and questions its premise in a later one.
- **Launch Without Load** — Capacity assumptions that are never measured are wrong in the unsafe direction, because designers estimate from the intended usage rather than the arrival pattern. Load appears as a step function at launch, not a ramp, so the first real test is also the first outage. TRIGGER: A ship/launch date with no load or soak test in the plan, or a stated concurrency/throughput number that is an estimate rather than a measurement.
- **Technology Seeking A Job** — When the differentiator is stated as a capability rather than a task someone was already trying to accomplish, the feature has no natural moment of use, so adoption requires teaching a new behavior instead of intercepting an existing one. Impressive capability and unused capability are fully compatible. TRIGGER: The spec leads with what the system can do ('we can embed / route / render / detect X') and the user's task appears only as a downstream illustration, or a hero feature has no named moment when someone would reach for it.
- **Craft On The Wrong Axis** — Engineering and design effort has a fixed budget and no automatic mapping to user-perceived value; teams that measure craft by internal difficulty will pour it into components whose quality is invisible in use, and ship a product whose expensive parts are the ones nobody experiences. TRIGGER: A diff or spec invests heavy effort in something the user never sees, touches, or measures — an internal abstraction, a component's hidden tolerances, a custom build pipeline, a rendering engine — while the user-facing behavior is unchanged.
- **Big-Bang Delivery** — When integration is scheduled once at the end, every incorrect assumption compounds silently for the whole project and all of them surface simultaneously, at the moment there is no budget left to act on them. Nothing is falsified until it is too late to be cheap. TRIGGER: A roadmap or plan whose milestones are all internal (design, build, integrate) with a single user-visible cutover at the end, and no shippable increment before it.
- **Distribution As An Afterthought** — Product work has a legible feedback loop (ship, see it work) and distribution does not, so engineering-led teams spend the entire runway on the loop that feels productive and reach the market with no channel built. By the time distribution becomes urgent, the money that would have funded channel experiments is already spent on the product. TRIGGER: A roadmap, spec, or milestone list where every item is a product capability and no item names a specific acquisition channel, or a plan that says marketing/launch/GTM happens "after v1".

## Set C

- **The Vanished Job** — A product whose value depends on a specific context persisting (a commute, an office, a partner runtime, a pricing regime) inherits that context's mortality; when the context changes, the product does not degrade gracefully, it becomes pointless overnight because the job it was hired for no longer exists. TRIGGER: A roadmap item's rationale depends on a user behavior, environment, or third-party surface continuing to exist — 'when they're commuting', 'in their agent's window', 'while the CI runs', 'via partner X's API'.
- **Preserving The Shape** — When a change is bolted onto an existing structure specifically to avoid disturbing it — because touching it would trigger a migration, recertification, or retraining cost — the new behavior inherits constraints it was never designed for, and the reason to avoid them becomes a reason not to fix them. TRIGGER: A change explicitly scoped to avoid touching an existing schema, interface, migration, or retraining/re-certification cost — phrases like "without changing the existing", "to avoid a migration", "keep it backward compatible" driving the design rather than following it.
- **Premature Automation** — Automating a process before doing it manually encodes a guess about the rules into code, and the code then prevents you from observing the exceptions that would have taught you the real rules. Manual work at small N is not a stopgap, it is the only instrument that reads the requirement. TRIGGER: A spec automates onboarding, setup, matching, curation, routing, or support before that process has been performed by hand enough times to have written down the exception cases.
- **Product Line Sprawl** — Each additional surface, SKU, or entry point consumes maintenance, documentation, support, and decision bandwidth permanently, while the marginal one is almost always worse than the median — so average quality falls monotonically as count rises, and the team's best people are spread across things no one would start today. TRIGGER: The plan adds a new surface, product, SKU, CLI command, MCP tool, page, or entry point while existing ones are unfinished, unowned, or undocumented; a countable surface inventory grows.
- **Second-System Rewrite** — A rewrite is scoped against the accumulated wishlist of everything the old system got wrong, so the new system is strictly larger than the one that already took years. Meanwhile the old system keeps shipping nothing, and the rewrite's real cost is the undocumented edge cases embedded in the code being discarded. TRIGGER: A proposal to rewrite a working module or surface from scratch, justified by cruft, where the new version is also scoped to fix known limitations of the old one.
- **Numbers Nobody Measured** — A quantitative claim with no measurement behind it still functions as one downstream — it gets cited, budgeted against, and used to close arguments — because the number's format carries authority its provenance does not. Organizations generate these numbers where the desired answer is known and the measurement is expensive. TRIGGER: A spec, README, or marketing line quotes a reliability, latency, uptime, accuracy, or coverage figure without naming the measurement that produced it.
- **Motion Without An Exit** — Vestibular responses to large-field motion are physiological, not preferential — a transition that reads as delightful to most users induces genuine nausea and vertigo in a minority, and without a system-level opt-out those users cannot use the product at all. TRIGGER: A diff adds parallax, zoom transitions, autoplay, scroll-linked animation, or page transitions — and does not gate them behind prefers-reduced-motion or an equivalent user setting.
- **Announcing The Successor** — Publicly declaring the current product inferior transfers demand to a replacement that does not yet exist, so the revenue collapses before the substitute can catch it. The honesty is real and the timing makes it self-inflicted. TRIGGER: Customer-facing copy, changelog, docs, or a public roadmap describes a currently shipping product, framing, or API as deprecated, weak, or superseded before its replacement is available.
- **Skipping The Unscalable** — Automating the first-user experience before doing it by hand encodes your guesses about what users need into software, and the automation then hides the disconfirming evidence. Manual onboarding is not inefficiency; it is the only instrument fine-grained enough to find the problem that the metrics summarize away. TRIGGER: A plan to build self-serve signup, an onboarding wizard, an email drip, an in-app tour, or a help center before roughly ten users have been onboarded by a founder in person.
- **Statistics Against Trust** — Answering a reported defect with its probability treats the user's problem as frequency when the actual damage is to the belief that the product's outputs can be relied on without checking. The probability argument is usually correct and always escalates, because it tells the reporter their experience does not count. TRIGGER: A response to a user-reported bug, data-loss report, or wrong-output complaint leads with how rare the condition is, or proposes closing it as won't-fix on frequency grounds.
- **Interface Without A Contract** — When two components exchange bare numbers or strings, the meaning (unit, timezone, encoding, ID namespace) lives only in each side's head. Nothing at the boundary can detect disagreement, so the mismatch propagates as plausible-looking data instead of an error. TRIGGER: A new API field, event payload, or cross-team/cross-service boundary passing raw numbers, timestamps, identifiers, or strings with no shared type, unit, or validation at the boundary.
- **Curated Demo Data** — Designs validated on hand-picked content encode assumptions about length, density, freshness, and correctness that real data violates on day one; the demo proves the layout, not the product, and the gap surfaces publicly at launch scale. TRIGGER: A design, screenshot, or demo uses seeded, curated, or short sample data; or a spec has no defined empty state, long-string, stale-data, error, and high-volume case for the surface being built.
- **Man-Month Arithmetic** — Adding people to a late project adds onboarding cost and communication paths (n²) before it adds throughput, and the work that is late is usually serially dependent, so the added capacity cannot be applied to the critical path. TRIGGER: A plan responding to schedule slip by adding engineers, parallel agents, or extra workstreams to the same late deliverable.
- **Segment-Blind PMF Survey** — The Sean Ellis 40% test averages across everyone who signed up, and a product with intense fit for a narrow segment plus indifference from tourists scores the same as a product nobody loves. The average hides the segment that would tell you what to build, so teams conclude they have no fit and pivot away from the users who actually had it. TRIGGER: A proposal to run the 40% test, NPS, or a satisfaction survey across the full user list, or a stated PMF/NPS number reported as one figure with no segment breakdown.
- **Silent Mode Divergence** — When one control's meaning depends on a mode the user cannot see at the moment of input, the interface accepts a correct-looking action and executes a different one; the operator's mental model and the machine's state diverge with no feedback to reconcile them. TRIGGER: A diff or spec adds a mode, toggle, view-state, or context in which the same control, keystroke, or input field produces different results — especially when the current mode is shown somewhere other than where the input happens.
