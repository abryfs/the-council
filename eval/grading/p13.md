# p13

**Prompt the founder typed:**
> read the copy on the landing page and tell me honestly if a stranger would understand what this does in ten seconds. I've read it so many times I can't tell anymore. don't be nice about it

_Context: Reviewing a landing page draft the night before sharing it_

For EACH set below, judge EACH pattern: is it genuinely relevant to this specific prompt — would surfacing it change or improve how an agent handles this request? Be strict. A pattern that is merely topically adjacent is NOT relevant.


## Set A

- **Error Text From Inside** — A message written from the system's state names a condition the user has no model for and no action attached to; it is technically accurate and operationally useless, so the user's only remaining move is to ask a human or abandon the task. TRIGGER: A diff adds or changes user-visible error, empty, or status copy that names an internal condition (state names, error codes, subsystem names, exception text) instead of what failed plus one concrete action the user can take.
- **Org Chart Shipped To Users** — A split that mirrors an internal boundary — separate app, brand, login, repo, or team — makes users pay the cost of a structure that exists for the builders' convenience. Users experience one job; splitting it forces them to re-onboard into a second product to accomplish what was previously one motion. TRIGGER: A split, rename, or separation in the product mirrors an internal boundary (two teams, two repos, two services, two panes) and forces the user to move between surfaces to complete one task.
- **Man-Month Arithmetic** — Adding people to a late project adds onboarding cost and communication paths (n²) before it adds throughput, and the work that is late is usually serially dependent, so the added capacity cannot be applied to the critical path. TRIGGER: A plan responding to schedule slip by adding engineers, parallel agents, or extra workstreams to the same late deliverable.
- **Segment-Blind PMF Survey** — The Sean Ellis 40% test averages across everyone who signed up, and a product with intense fit for a narrow segment plus indifference from tourists scores the same as a product nobody loves. The average hides the segment that would tell you what to build, so teams conclude they have no fit and pivot away from the users who actually had it. TRIGGER: A proposal to run the 40% test, NPS, or a satisfaction survey across the full user list, or a stated PMF/NPS number reported as one figure with no segment breakdown.
- **Root Cause Singular** — Five-whys terminates at the first cause that is both technical and fixable, because that node is where the search stops feeling productive. The organizational conditions that let the technical fault reach production are upstream of that stopping point, so they survive the fix and reproduce it. TRIGGER: An incident writeup, postmortem, or bug analysis names exactly one root cause and one code-level fix, with no finding about how the defect passed review or shipped.
- **Job Mistaken For Demographic** — Segmenting by who the user is produces feature requests that correlate with the segment but explain nothing causal, so improvements aimed at the persona miss the situation that actually triggered the purchase. Two people in the same demographic hire the product for opposite jobs, and averaging them produces a product for neither. TRIGGER: Requirements are segmented by who the user is (role, persona, seniority, company size, 'founders vs engineers') rather than by the situation and task at the moment of use.
- **Control Plane Inside The Blast Radius** — When the tooling that observes, deploys, authenticates, or rolls back depends on the system it manages, the first failure removes the means of recovery. Mean time to repair is then set by whatever out-of-band path was never built. TRIGGER: A design where monitoring, deploy, auth, feature flags, or the rollback path runs on, resolves through, or authenticates against the same system it controls.
- **Chasing The Moving Baseline** — Rescoping in-flight work to adopt a newer substrate resets the completion clock while the substrate keeps advancing, so the gap between what you have and what is current never closes — each adoption is individually justified and the sequence never terminates. TRIGGER: In-flight work is rescoped to adopt a newly released model, framework, engine, API version, or internal abstraction before the current version has shipped to anyone.
- **Feature Parity Positioning** — Positioning your product as a better version of an incumbent asks the customer to compare on the incumbent's chosen axes, where the incumbent's scale wins by construction, and it gives no one a reason to bear switching cost. Parity is also unbounded work: matching the feature list is a treadmill the incumbent sets the speed of. TRIGGER: A positioning doc, landing page, or spec that frames the product as "X but better/faster/cheaper", or leads with a feature-comparison table against a named incumbent.
- **Silent Mode Divergence** — When one control's meaning depends on a mode the user cannot see at the moment of input, the interface accepts a correct-looking action and executes a different one; the operator's mental model and the machine's state diverge with no feedback to reconcile them. TRIGGER: A diff or spec adds a mode, toggle, view-state, or context in which the same control, keystroke, or input field produces different results — especially when the current mode is shown somewhere other than where the input happens.
- **Reused Component, New Envelope** — A component's correctness depends on the operating envelope it was validated in — value ranges, clock rates, load profile. Reuse carries the code but not the envelope, and the assumption that made it safe becomes silently false. TRIGGER: A diff or plan that lifts an existing module, service, query, or library into a new scale, platform, region, or traffic profile described as reusing it "unchanged" or "as-is".
- **Retroactive Value-Metric Change** — Customers price their own business models on your billing unit; changing that unit — especially applying it to work already shipped — invalidates their planning and reads as a breach rather than a price rise. The revolt costs more in trust and churn than the new revenue was ever worth, because the affected customers are by definition your most successful ones. TRIGGER: A pricing change that alters the billing unit (seats→usage, revenue→installs, flat→metered), reprices existing contracts, or applies to activity that already happened.
- **Stated Preference Trap** — Users accurately report what they want and cannot report what it costs, because the cost (latency, density, decision load) is a property of the system, not of the wish. Delivering the requested thing literally can move the metric the wrong way. TRIGGER: A spec justifies a feature with "users asked for it," a feature-request count, survey results, or a support-ticket theme — with no statement of what the addition costs in load time, screen density, or steps.
- **Seat Pricing Punishes Adoption** — When a product's value rises with how many colleagues are on it but the price also rises per colleague, the buyer's rational move is to restrict the rollout — which starves the exact network effect the product depends on. The pricing model actively fights the product's mechanism, and the resulting low penetration reads to the team as weak demand. TRIGGER: A pricing page or spec charging per seat, per user, or per member for a product whose core value requires a whole team, or charging full price for read-only/viewer/observer roles.
- **No Beachhead** — A message aimed at everyone is specific to no one, so it fails the only test that matters early: can one user explain it to the next user in a sentence. Without a defined first customer, price, channel, and objection-handling all become guesses, and there is no dense population in which word of mouth can propagate. TRIGGER: TAM-driven sizing, "for any team / any company / everyone who...", or a launch plan listing three or more personas with no ranking of which one ships first.

## Set B

- **Seat Pricing Punishes Adoption** — When a product's value rises with how many colleagues are on it but the price also rises per colleague, the buyer's rational move is to restrict the rollout — which starves the exact network effect the product depends on. The pricing model actively fights the product's mechanism, and the resulting low penetration reads to the team as weak demand. TRIGGER: A pricing page or spec charging per seat, per user, or per member for a product whose core value requires a whole team, or charging full price for read-only/viewer/observer roles.
- **Feature Parity Positioning** — Positioning your product as a better version of an incumbent asks the customer to compare on the incumbent's chosen axes, where the incumbent's scale wins by construction, and it gives no one a reason to bear switching cost. Parity is also unbounded work: matching the feature list is a treadmill the incumbent sets the speed of. TRIGGER: A positioning doc, landing page, or spec that frames the product as "X but better/faster/cheaper", or leads with a feature-comparison table against a named incumbent.
- **Premature Automation** — Automating a process before doing it manually encodes a guess about the rules into code, and the code then prevents you from observing the exceptions that would have taught you the real rules. Manual work at small N is not a stopgap, it is the only instrument that reads the requirement. TRIGGER: A spec automates onboarding, setup, matching, curation, routing, or support before that process has been performed by hand enough times to have written down the exception cases.
- **Skipping The Unscalable** — Automating the first-user experience before doing it by hand encodes your guesses about what users need into software, and the automation then hides the disconfirming evidence. Manual onboarding is not inefficiency; it is the only instrument fine-grained enough to find the problem that the metrics summarize away. TRIGGER: A plan to build self-serve signup, an onboarding wizard, an email drip, an in-app tour, or a help center before roughly ten users have been onboarded by a founder in person.
- **The Untested Restore** — Backups are write-path artifacts; nothing exercises the read path until an emergency, so silent failures (empty buckets, wrong flags, expired credentials) accumulate undetected. The existence of a backup job is not evidence that a restore is possible. TRIGGER: A spec, runbook, or reply that mentions backups, snapshots, replicas, or disaster recovery as mitigation, with no restore drill or verification step.
- **The Big-Bang Relaunch** — Replacing a shipped surface wholesale in one release couples a hundred independent bets into a single irreversible event, so you cannot tell which change caused the loss, and existing users pay the full re-learning cost on a day they did not choose. Habitual users are the ones who notice most, and they are the ones you can least afford to lose. TRIGGER: A plan replaces an existing shipped surface in one release — 'v2 replaces v1', 'retire the old frame', 'cut over' — with no dual-run, opt-in, or staged migration.
- **Segment-Blind PMF Survey** — The Sean Ellis 40% test averages across everyone who signed up, and a product with intense fit for a narrow segment plus indifference from tourists scores the same as a product nobody loves. The average hides the segment that would tell you what to build, so teams conclude they have no fit and pivot away from the users who actually had it. TRIGGER: A proposal to run the 40% test, NPS, or a satisfaction survey across the full user list, or a stated PMF/NPS number reported as one figure with no segment breakdown.
- **Redesign Riding A Rewrite** — Shipping a new surface on top of a new backend at once destroys attribution and rollback simultaneously: you cannot tell whether users hate the design or the bugs, and you cannot revert the design because the old one no longer has a system underneath it. TRIGGER: A plan couples a visual/IA redesign with a platform migration, framework swap, schema change, or API rewrite in one release — or the rollback plan for a UI change is "revert the deploy" when the data model also changed.
- **Guessing The Bottleneck** — Intuition about performance is trained on the code you read, while cost lives in behavior you cannot see — allocation, cache misses, scheduler and GC intervals, tail latency. Optimizing before profiling spends effort on the wrong axis and hides the real cause behind a changed baseline. TRIGGER: A diff or plan doing performance work — caching, batching, async, index, language/runtime swap — with no profile, benchmark, or production measurement cited, or a claim that something "should be faster".
- **Exit Reason Assumed** — Churn explanations default to the most legible variable — price, salary, performance — because it is the one already instrumented. The actual reasons are relational and only obtainable by asking, so the retention fix targets the wrong lever and produces no change, which is then read as the problem being intractable. TRIGGER: An explanation of attrition, churn, drop-off, or non-adoption asserts a cause (price, speed, missing feature) without citing anything the departed users or teammates actually said.
- **Motion Without An Exit** — Vestibular responses to large-field motion are physiological, not preferential — a transition that reads as delightful to most users induces genuine nausea and vertigo in a minority, and without a system-level opt-out those users cannot use the product at all. TRIGGER: A diff adds parallax, zoom transitions, autoplay, scroll-linked animation, or page transitions — and does not gate them behind prefers-reduced-motion or an equivalent user setting.
- **Product Line Sprawl** — Each additional surface, SKU, or entry point consumes maintenance, documentation, support, and decision bandwidth permanently, while the marginal one is almost always worse than the median — so average quality falls monotonically as count rises, and the team's best people are spread across things no one would start today. TRIGGER: The plan adds a new surface, product, SKU, CLI command, MCP tool, page, or entry point while existing ones are unfinished, unowned, or undocumented; a countable surface inventory grows.
- **The Metric That Moves Alone** — A proxy metric that can rise without the underlying job being served will be optimized directly, because it is the thing that is measured and reported; the product then drifts toward whatever produces the number, and the gap between metric and job widens fastest exactly when the metric looks best. TRIGGER: A success criterion is a count that can increase while the underlying job goes unserved — events emitted, broadcasts sent, tool calls, DAU, sign-ups, page views — with no paired measure of whether the recipient acted on it.
- **Announcing The Successor** — Publicly declaring the current product inferior transfers demand to a replacement that does not yet exist, so the revenue collapses before the substitute can catch it. The honesty is real and the timing makes it self-inflicted. TRIGGER: Customer-facing copy, changelog, docs, or a public roadmap describes a currently shipping product, framing, or API as deprecated, weak, or superseded before its replacement is available.
- **Two-Way Door Deliberated** — Applying heavyweight process to a reversible decision costs more than being wrong would have, and the delay itself removes the cheapest source of information — shipping it and watching. Organizations default to the heavy process for everything because the process was designed around the rare irreversible case. TRIGGER: An easily reversible change — copy, layout, a default value, ordering, a flag's initial setting, a threshold — is escalated to a spec, a review cycle, or a founder decision.

## Set C

- **Metaphor Fusion** — A product that fuses several familiar categories inherits none of their mental models, so a new user has no prior to fall back on and no one-sentence description to pass along; adoption then depends on formal explanation, which does not travel. TRIGGER: A spec describes the surface by joining categories with "and" ("it's a doc and a chat and a board"), unifies two existing product surfaces into one, or cannot state what the thing is in one sentence a non-user would repeat.
- **Positioning To The Wrong Frame** — The category you claim determines which competitors the buyer mentally lines you up against and which features they treat as table stakes. Claim a broad, incumbent-owned category and your genuine differentiator is scored as a minor feature; claim the frame where that differentiator is the whole point and the same product becomes the obvious choice. TRIGGER: Copy or a spec that names a broad established category ("CRM", "project management", "observability", "coordination layer") without naming the specific buyer and the specific alternative they'd otherwise use.
- **No Beachhead** — A message aimed at everyone is specific to no one, so it fails the only test that matters early: can one user explain it to the next user in a sentence. Without a defined first customer, price, channel, and objection-handling all become guesses, and there is no dense population in which word of mouth can propagate. TRIGGER: TAM-driven sizing, "for any team / any company / everyone who...", or a launch plan listing three or more personas with no ranking of which one ships first.
- **Technology Seeking A Job** — When the differentiator is stated as a capability rather than a task someone was already trying to accomplish, the feature has no natural moment of use, so adoption requires teaching a new behavior instead of intercepting an existing one. Impressive capability and unused capability are fully compatible. TRIGGER: The spec leads with what the system can do ('we can embed / route / render / detect X') and the user's task appears only as a downstream illustration, or a hero feature has no named moment when someone would reach for it.
- **Hype Ahead Of Usability** — A long, expert-narrated demo can make an unexplainable product look compelling to an audience primed to be impressed, and invite scarcity converts that impression into signups. Neither tests the actual constraint — whether one ordinary user can explain the product to the next one — so the waitlist converts into a cohort that opens it once and never returns. TRIGGER: A launch plan gated by waitlist or invite codes, or a demo script/video longer than about two minutes that requires narration to make the product legible.
- **Feature Parity Positioning** — Positioning your product as a better version of an incumbent asks the customer to compare on the incumbent's chosen axes, where the incumbent's scale wins by construction, and it gives no one a reason to bear switching cost. Parity is also unbounded work: matching the feature list is a treadmill the incumbent sets the speed of. TRIGGER: A positioning doc, landing page, or spec that frames the product as "X but better/faster/cheaper", or leads with a feature-comparison table against a named incumbent.
- **Job Mistaken For Demographic** — Segmenting by who the user is produces feature requests that correlate with the segment but explain nothing causal, so improvements aimed at the persona miss the situation that actually triggered the purchase. Two people in the same demographic hire the product for opposite jobs, and averaging them produces a product for neither. TRIGGER: Requirements are segmented by who the user is (role, persona, seniority, company size, 'founders vs engineers') rather than by the situation and task at the moment of use.
- **Numbers Nobody Measured** — A quantitative claim with no measurement behind it still functions as one downstream — it gets cited, budgeted against, and used to close arguments — because the number's format carries authority its provenance does not. Organizations generate these numbers where the desired answer is known and the measurement is expensive. TRIGGER: A spec, README, or marketing line quotes a reliability, latency, uptime, accuracy, or coverage figure without naming the measurement that produced it.
- **Beautiful Prototype Bias** — Perceived usability tracks aesthetics more tightly than actual usability, so a polished mock or prototype scores well in review and testing regardless of whether the interaction works; the visual finish suppresses exactly the criticism the review exists to surface. TRIGGER: A design is approved from a high-fidelity mock, Figma prototype, or rendered screenshot; or usability testing is run on a visually finished build without a low-fidelity or degraded-data comparison.
- **Error Text From Inside** — A message written from the system's state names a condition the user has no model for and no action attached to; it is technically accurate and operationally useless, so the user's only remaining move is to ask a human or abandon the task. TRIGGER: A diff adds or changes user-visible error, empty, or status copy that names an internal condition (state names, error codes, subsystem names, exception text) instead of what failed plus one concrete action the user can take.
- **Signifier Erasure** — Flattening removes borders, fills, and shadows — which are not decoration but the clickability cues users scan for — so the visual noise drops while the search cost rises; the page looks calmer in a screenshot and costs more per task in use. TRIGGER: A diff removes borders, background fills, underlines, or shadows from interactive elements, converts buttons to text/ghost buttons, or a spec asks to "make it cleaner / flatter / less chrome."
- **Stated Preference Trap** — Users accurately report what they want and cannot report what it costs, because the cost (latency, density, decision load) is a property of the system, not of the wish. Delivering the requested thing literally can move the metric the wrong way. TRIGGER: A spec justifies a feature with "users asked for it," a feature-request count, survey results, or a support-ticket theme — with no statement of what the addition costs in load time, screen density, or steps.
- **Distribution As An Afterthought** — Product work has a legible feedback loop (ship, see it work) and distribution does not, so engineering-led teams spend the entire runway on the loop that feels productive and reach the market with no channel built. By the time distribution becomes urgent, the money that would have funded channel experiments is already spent on the product. TRIGGER: A roadmap, spec, or milestone list where every item is a product capability and no item names a specific acquisition channel, or a plan that says marketing/launch/GTM happens "after v1".
- **Preference-First Framing** — When the decision-maker states their conclusion before soliciting input, every subsequent contribution is scored by the contributor against the cost of contradicting them, not against the evidence. Input arrives, so the process looks consultative, but it has been filtered to what survives disagreement with the boss. TRIGGER: A request to review, sign off on, or implement an approach whose author has already stated a preferred outcome, or a message shaped as "here's what we're doing — thoughts?"
- **Curated Demo Data** — Designs validated on hand-picked content encode assumptions about length, density, freshness, and correctness that real data violates on day one; the demo proves the layout, not the product, and the gap surfaces publicly at launch scale. TRIGGER: A design, screenshot, or demo uses seeded, curated, or short sample data; or a spec has no defined empty state, long-string, stale-data, error, and high-volume case for the surface being built.
