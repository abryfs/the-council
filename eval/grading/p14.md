# p14

**Prompt the founder typed:**
> I want to add email digests — daily summary of what happened in your workspace. Before you write anything, tell me what you'd need to decide. I've been burned by half-designed notification features before.

_Context: Adding a feature that touches the notification system_

For EACH set below, judge EACH pattern: is it genuinely relevant to this specific prompt — would surfacing it change or improve how an agent handles this request? Be strict. A pattern that is merely topically adjacent is NOT relevant.


## Set A

- **Prompt Inflation** — Each interruption's cost is paid by every user on every occurrence, while its benefit accrues only in the rare case it prevents; past a low frequency threshold users learn to dismiss the class reflexively, which destroys the signal value of the one prompt that mattered. TRIGGER: A diff adds a confirmation dialog, permission prompt, toast, banner, badge, or notification to a flow that already has one — or a spec's answer to a risk is "warn the user."
- **Assistant That Interrupts** — A proactive helper must infer intent from weak signals, so its false-positive rate is high, and every false positive costs a competent user an interruption plus a dismissal. The novice's occasional benefit is charged to the expert on every session, and dismissal becomes the learned default. TRIGGER: A spec adds a proactive tip, coach mark, onboarding tour, suggestion popup, or AI assistant that appears without the user requesting it, based on inferred intent.
- **Alert As The Fix** — Adding a warning to an unactioned stream does not create action; it raises the base rate of ignorable signals, which lowers the probability that any specific one is investigated. The detection exists on paper and is absent in practice. TRIGGER: A proposed remediation that consists of logging a warning, emitting a metric, or adding a monitor — with no owner, threshold, or defined response — or a codebase with existing warnings nobody triages.
- **The Metric That Moves Alone** — A proxy metric that can rise without the underlying job being served will be optimized directly, because it is the thing that is measured and reported; the product then drifts toward whatever produces the number, and the gap between metric and job widens fastest exactly when the metric looks best. TRIGGER: A success criterion is a count that can increase while the underlying job goes unserved — events emitted, broadcasts sent, tool calls, DAU, sign-ups, page views — with no paired measure of whether the recipient acted on it.
- **Curated Demo Data** — Designs validated on hand-picked content encode assumptions about length, density, freshness, and correctness that real data violates on day one; the demo proves the layout, not the product, and the gap surfaces publicly at launch scale. TRIGGER: A design, screenshot, or demo uses seeded, curated, or short sample data; or a spec has no defined empty state, long-string, stale-data, error, and high-volume case for the surface being built.
- **Cold Start Ignored** — Any product whose value comes from other people's content or presence is worthless to user one, so the acquisition funnel and the retention mechanism fight each other: every user you bring sees an empty room and leaves, and their departure makes the room emptier. The founders must manufacture the initial density by hand because no channel can outrun an empty product. TRIGGER: A spec for a feed, map, marketplace, roster, leaderboard, directory, team view, or any social surface, with no stated plan for what a first user or solo user sees.
- **Interface Without A Contract** — When two components exchange bare numbers or strings, the meaning (unit, timezone, encoding, ID namespace) lives only in each side's head. Nothing at the boundary can detect disagreement, so the mismatch propagates as plausible-looking data instead of an error. TRIGGER: A new API field, event payload, or cross-team/cross-service boundary passing raw numbers, timestamps, identifiers, or strings with no shared type, unit, or validation at the boundary.
- **Confirmation Instead Of Reversal** — An "Are you sure?" dialog is a speed bump, not a safeguard — users confirm the action they believe they are taking, so the dialog passes exactly when the user is already wrong. Only a reversal path bounds the damage after the mistaken confirm. TRIGGER: A diff or spec guards a destructive, irreversible, or broadcast-to-others action with a confirmation dialog, checkbox, or type-to-confirm — and no undo window, recall, dry-run, or reversal path is specified.
- **Global Blast Radius** — Treating rules, content, or config as "not code" routes it around the staged rollout that protects code, so a bad artifact reaches 100% of the fleet in one push. If the failure mode also prevents the machine from booting, there is no remote path to roll back. TRIGGER: A change shipping to all users, machines, or tenants simultaneously — or a data/config/rules/prompt/template update path that bypasses the canary and staged-rollout used for code.
- **One-Way Door Misread** — Anything external parties can build against — a public API, tool name, URL scheme, event type, wire field, file format — becomes unrevocable the moment someone depends on it, because the cost of removal is paid by them and shows up as broken trust rather than a rollback. Such decisions get made at the speed of a reversible one because the diff looks small. TRIGGER: A diff or spec publishes something external parties will depend on: a public API endpoint, an MCP or CLI tool name, an event type or enum value, a URL scheme, a config key, an on-disk or wire format.
- **Error Text From Inside** — A message written from the system's state names a condition the user has no model for and no action attached to; it is technically accurate and operationally useless, so the user's only remaining move is to ask a human or abandon the task. TRIGGER: A diff adds or changes user-visible error, empty, or status copy that names an internal condition (state names, error codes, subsystem names, exception text) instead of what failed plus one concrete action the user can take.
- **Stated Preference Trap** — Users accurately report what they want and cannot report what it costs, because the cost (latency, density, decision load) is a property of the system, not of the wish. Delivering the requested thing literally can move the metric the wrong way. TRIGGER: A spec justifies a feature with "users asked for it," a feature-request count, survey results, or a support-ticket theme — with no statement of what the addition costs in load time, screen density, or steps.
- **Accessibility As Post-Ship Bug** — Accessibility is decided by structure — semantics, focus order, names, contrast — which is fixed at the moment the component is built; deferring it converts a design constraint into a rewrite, and in many jurisdictions into legal exposure that no backlog priority can defer. TRIGGER: A spec or diff ships an interactive component with a11y noted as follow-up, or introduces custom interactive markup (div-as-button, custom modal, canvas UI, drag-and-drop) with no keyboard path, focus management, or accessible name.
- **The Deck Instead Of The Memo** — Bullets let a proposal omit the connective tissue — the constraint, the alternative rejected, the thing that would make this wrong — because a bullet has no grammar that requires them. The gaps are invisible to the reader and often to the author, who mistakes the deck's completeness for the argument's. TRIGGER: A plan or spec arrives as a feature list, bullet outline, table, or phase grid with no prose section stating the problem, the constraints, and what evidence would falsify the approach.
- **Premature Platformization** — A protocol, plugin API, or generality invented before one concrete use is in production is designed against imagined consumers, so it optimizes for flexibility no one needs while missing the constraint the first real user would have imposed. It also raises the cost of every subsequent change, because generality is what you promise not to break. TRIGGER: A spec introduces a protocol, plugin API, extension point, federation model, or abstraction justified by future third parties ('so others can build on it', 'generic enough for N cases') before one concrete case is in production.

## Set B

- **Skipping The Unscalable** — Automating the first-user experience before doing it by hand encodes your guesses about what users need into software, and the automation then hides the disconfirming evidence. Manual onboarding is not inefficiency; it is the only instrument fine-grained enough to find the problem that the metrics summarize away. TRIGGER: A plan to build self-serve signup, an onboarding wizard, an email drip, an in-app tour, or a help center before roughly ten users have been onboarded by a founder in person.
- **Boiling The Ocean** — When v1 requires three or more unproven components to all work at once, the probability of shipping is the product of each part's odds, and no single part can be validated until the others exist. Learning is deferred until the whole thing is done, which is exactly when it is most expensive to be wrong. TRIGGER: A spec or plan lists three or more novel, unproven components (new runtime, new data model, new rendering surface, new protocol) that must all work before anything is usable.
- **Discoverability Mistaken For Absence** — Users request features they cannot find, so a request queue reads as a gap list when it is often a findability report; building the requested thing a second time adds surface area without adding capability and makes the original even harder to find. TRIGGER: A ticket or spec proposes building a capability that may already exist somewhere in the product — "add a way to X," "users can't do Y" — without a check of whether X/Y already ships behind a menu, flag, or command.
- **Premature Platformization** — A protocol, plugin API, or generality invented before one concrete use is in production is designed against imagined consumers, so it optimizes for flexibility no one needs while missing the constraint the first real user would have imposed. It also raises the cost of every subsequent change, because generality is what you promise not to break. TRIGGER: A spec introduces a protocol, plugin API, extension point, federation model, or abstraction justified by future third parties ('so others can build on it', 'generic enough for N cases') before one concrete case is in production.
- **Cofounder Equity Without Vesting** — Equity granted without vesting or a cliff prices a contribution before it has happened, and the grant survives the contributor's departure, disagreement, or non-performance. The dispute surfaces at the financing or acquisition that makes the equity worth litigating, which is the worst possible moment to have it. TRIGGER: A cofounder split, advisor grant, contractor equity arrangement, or early-employee offer is described with a percentage but no vesting schedule, cliff, or repurchase right.
- **Relearning Tax Ignored** — In a product people use daily, the interface is a motor habit; moving things resets that habit for every existing user at once, so the cost is paid on day one by everyone while the benefit accrues slowly to newcomers who do not exist yet. The new-user gain almost never exceeds the aggregate relearning loss. TRIGGER: A spec reorganizes navigation, moves an existing feature to a new location, renames a primary action, or changes the information architecture of a product that already has habituated daily users.
- **Prompt Inflation** — Each interruption's cost is paid by every user on every occurrence, while its benefit accrues only in the rare case it prevents; past a low frequency threshold users learn to dismiss the class reflexively, which destroys the signal value of the one prompt that mattered. TRIGGER: A diff adds a confirmation dialog, permission prompt, toast, banner, badge, or notification to a flow that already has one — or a spec's answer to a risk is "warn the user."
- **Premature Automation** — Automating a process before doing it manually encodes a guess about the rules into code, and the code then prevents you from observing the exceptions that would have taught you the real rules. Manual work at small N is not a stopgap, it is the only instrument that reads the requirement. TRIGGER: A spec automates onboarding, setup, matching, curation, routing, or support before that process has been performed by hand enough times to have written down the exception cases.
- **Announcing The Successor** — Publicly declaring the current product inferior transfers demand to a replacement that does not yet exist, so the revenue collapses before the substitute can catch it. The honesty is real and the timing makes it self-inflicted. TRIGGER: Customer-facing copy, changelog, docs, or a public roadmap describes a currently shipping product, framing, or API as deprecated, weak, or superseded before its replacement is available.
- **The Never-Restarted Subsystem** — Long-lived services grow past the scale their cold-start path was designed for, and because that path never runs, the regression is invisible until the day you need it. Recovery time then becomes an unknown discovered during the outage. TRIGGER: A design involving a long-lived stateful service, cache, or index, where warm-up, rebuild, replay, or cold-start time is unstated or assumed fast.
- **Big-Bang Delivery** — When integration is scheduled once at the end, every incorrect assumption compounds silently for the whole project and all of them surface simultaneously, at the moment there is no budget left to act on them. Nothing is falsified until it is too late to be cheap. TRIGGER: A roadmap or plan whose milestones are all internal (design, build, integrate) with a single user-visible cutover at the end, and no shippable increment before it.
- **Chasing The Moving Baseline** — Rescoping in-flight work to adopt a newer substrate resets the completion clock while the substrate keeps advancing, so the gap between what you have and what is current never closes — each adoption is individually justified and the sequence never terminates. TRIGGER: In-flight work is rescoped to adopt a newly released model, framework, engine, API version, or internal abstraction before the current version has shipped to anyone.
- **Foundation Before First User** — Infrastructure built for a feature that does not exist has no consumer to falsify its design, so its interface is derived from imagination and calcifies before contact. The dependent feature then inherits constraints from a substrate that was never tested against the real requirement. TRIGGER: A spec adds infrastructure — an index, cache, schema, consolidation pass, worker, centroid set, router — whose only named consumer is a feature not yet built or validated.
- **Retroactive Value-Metric Change** — Customers price their own business models on your billing unit; changing that unit — especially applying it to work already shipped — invalidates their planning and reads as a breach rather than a price rise. The revolt costs more in trust and churn than the new revenue was ever worth, because the affected customers are by definition your most successful ones. TRIGGER: A pricing change that alters the billing unit (seats→usage, revenue→installs, flat→metered), reprices existing contracts, or applies to activity that already happened.
- **Premature Scaling** — Capacity built ahead of demand converts fixed costs into a deadline: the burn rate now sets how long you have to find the demand, rather than the demand setting how much you build. Because the capacity is sunk, the team also loses the option to change the shape of the business when the early signal comes back wrong. TRIGGER: A plan that adds headcount, geographies, warehouses, regions, or provisioned infrastructure capacity on a schedule rather than in response to a measured demand signal; "build it so it scales to N" before N/100 exists.

## Set C

- **Distribution As An Afterthought** — Product work has a legible feedback loop (ship, see it work) and distribution does not, so engineering-led teams spend the entire runway on the loop that feels productive and reach the market with no channel built. By the time distribution becomes urgent, the money that would have funded channel experiments is already spent on the product. TRIGGER: A roadmap, spec, or milestone list where every item is a product capability and no item names a specific acquisition channel, or a plan that says marketing/launch/GTM happens "after v1".
- **Cold Start Ignored** — Any product whose value comes from other people's content or presence is worthless to user one, so the acquisition funnel and the retention mechanism fight each other: every user you bring sees an empty room and leaves, and their departure makes the room emptier. Without a defined first customer, price, channel, and objection-handling all become guesses, and there is no dense population in which word of mouth can propagate. TRIGGER: TAM-driven sizing, "for any team / any company / everyone who...", or a launch plan listing three or more personas with no ranking of which one ships first.

- **Control Swallowed By Screen** — A screen control demands visual attention and offers no tactile confirmation, so moving a frequent or eyes-busy action into a menu converts a sub-second muscle-memory operation into a look-navigate-aim-verify loop. The cost is invisible in a demo where the user is already looking at the screen. TRIGGER: A spec relocates a frequent, urgent, or eyes-busy control into a screen, menu, submenu, command palette, or gesture — replacing a dedicated key, button, or always-visible affordance.
- **Signifier Erasure** — Flattening removes borders, fills, and shadows — which are not decoration but the clickability cues users scan for — so the visual noise drops while the search cost rises; the page looks calmer in a screenshot and costs more per task in use. TRIGGER: A diff removes borders, background fills, underlines, or shadows from interactive elements, converts buttons to text/ghost buttons, or a spec asks to "make it cleaner / flatter / less chrome."
- **CAC Buried In COGS** — When customers churn faster than they repay acquisition cost, acquisition spend stops being an investment and becomes a recurring cost of goods — every dollar of revenue requires a fresh dollar of marketing forever. Reporting new-customer counts instead of cohort curves hides this, because the top line grows right up until spend stops. TRIGGER: A growth dashboard, OKR, or investor update whose headline metric is signups, downloads, trials, or new customers, with no cohort retention curve or LTV:CAC ratio alongside it.

Reuse carries the code but not the envelope, and the assumption that made it safe becomes silently false. TRIGGER: A diff or plan that lifts an existing module, service, query, or library into a new scale, platform, region, or traffic profile described as reusing it "unchanged" or "as-is".
