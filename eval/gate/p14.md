# p14

**Prompt:**
> I want to add email digests — daily summary of what happened in your workspace. Before you write anything, tell me what you'd need to decide. I've been burned by half-designed notification features before.

_Context: Adding a feature that touches the notification system_


## Candidates (8, ranked by lexical match)

- **Skipping The Unscalable** [warn] — Automating the first-user experience before doing it by hand encodes your guesses about what users need into software, and the automation then hides the disconfirming evidence. Manual onboarding is not inefficiency; it is the only instrument fine-grained enough to find the problem that the metrics summarize away. TRIGGER: A plan to build self-serve signup, an onboarding wizard, an email drip, an in-app tour, or a help center before roughly ten users have been onboarded by a founder in person.
- **Boiling The Ocean** [block] — When v1 requires three or more unproven components to all work at once, the probability of shipping is the product of each part's odds, and no single part can be validated until the others exist. Learning is deferred until the whole thing is done, which is exactly when it is most expensive to be wrong. TRIGGER: A spec or plan lists three or more novel, unproven components (new runtime, new data model, new rendering surface, new protocol) that must all work before anything is usable.
- **Discoverability Mistaken For Absence** [note] — Users request features they cannot find, so a request queue reads as a gap list when it is often a findability report; building the requested thing a second time adds surface area without adding capability and makes the original even harder to find. TRIGGER: A ticket or spec proposes building a capability that may already exist somewhere in the product — "add a way to X," "users can't do Y" — without a check of whether X/Y already ships behind a menu, flag, or command.
- **Premature Platformization** [block] — A protocol, plugin API, or generality invented before one concrete use is in production is designed against imagined consumers, so it optimizes for flexibility no one needs while missing the constraint the first real user would have imposed. It also raises the cost of every subsequent change, because generality is what you promise not to break. TRIGGER: A spec introduces a protocol, plugin API, extension point, federation model, or abstraction justified by future third parties ('so others can build on it', 'generic enough for N cases') before one concrete case is in production.
- **Cofounder Equity Without Vesting** [block] — Equity granted without vesting or a cliff prices a contribution before it has happened, and the grant survives the contributor's departure, disagreement, or non-performance. The dispute surfaces at the financing or acquisition that makes the equity worth litigating, which is the worst possible moment to have it. TRIGGER: A cofounder split, advisor grant, contractor equity arrangement, or early-employee offer is described with a percentage but no vesting schedule, cliff, or repurchase right.
- **Relearning Tax Ignored** [warn] — In a product people use daily, the interface is a motor habit; moving things resets that habit for every existing user at once, so the cost is paid on day one by everyone while the benefit accrues slowly to newcomers who do not exist yet. The new-user gain almost never exceeds the aggregate relearning loss. TRIGGER: A spec reorganizes navigation, moves an existing feature to a new location, renames a primary action, or changes the information architecture of a product that already has habituated daily users.
- **Prompt Inflation** [warn] — Each interruption's cost is paid by every user on every occurrence, while its benefit accrues only in the rare case it prevents; past a low frequency threshold users learn to dismiss the class reflexively, which destroys the signal value of the one prompt that mattered. TRIGGER: A diff adds a confirmation dialog, permission prompt, toast, banner, badge, or notification to a flow that already has one — or a spec's answer to a risk is "warn the user."
- **Premature Automation** [warn] — Automating a process before doing it manually encodes a guess about the rules into code, and the code then prevents you from observing the exceptions that would have taught you the real rules. Manual work at small N is not a stopgap, it is the only instrument that reads the requirement. TRIGGER: A spec automates onboarding, setup, matching, curation, routing, or support before that process has been performed by hand enough times to have written down the exception cases.
