# p06

**Prompt:**
> prod is serving stale data to some users but not others. cache layer is redis, ttl is 300s. I already tried flushing and it came back within a couple minutes. where do I even start

_Context: Production incident in progress, users reporting stale data_


## Candidates (8, ranked by lexical match)

- **The Never-Restarted Subsystem** [warn] — Long-lived services grow past the scale their cold-start path was designed for, and because that path never runs, the regression is invisible until the day you need it. Recovery time then becomes an unknown discovered during the outage. TRIGGER: A design involving a long-lived stateful service, cache, or index, where warm-up, rebuild, replay, or cold-start time is unstated or assumed fast.
- **Discoverability Mistaken For Absence** [note] — Users request features they cannot find, so a request queue reads as a gap list when it is often a findability report; building the requested thing a second time adds surface area without adding capability and makes the original even harder to find. TRIGGER: A ticket or spec proposes building a capability that may already exist somewhere in the product — "add a way to X," "users can't do Y" — without a check of whether X/Y already ships behind a menu, flag, or command.
- **Curated Demo Data** [warn] — Designs validated on hand-picked content encode assumptions about length, density, freshness, and correctness that real data violates on day one; the demo proves the layout, not the product, and the gap surfaces publicly at launch scale. TRIGGER: A design, screenshot, or demo uses seeded, curated, or short sample data; or a spec has no defined empty state, long-string, stale-data, error, and high-volume case for the surface being built.
- **Second-System Effect** [block] — The v2 becomes the dumping ground for every idea deferred from v1, and because none of them has shipped, none can be cut on evidence. Scope grows faster than the team can integrate, so the system never reaches a state where any single feature is finishable. TRIGGER: A spec or plan for a v2/next-gen version that lists features deferred from v1, or bundles a new data model + new UI + new extensibility layer in one release.
- **Innovation Token Overdraft** [warn] — Every unfamiliar technology carries unknown failure modes that only surface under production load, and each one consumes the same scarce resource: engineer attention during incidents. Spending several at once means every outage has multiple novel suspects and no one has intuition about any of them. TRIGGER: A diff or spec that introduces a new datastore, language, queue, or orchestration layer — especially two or more in the same change — where an already-running component would do.
- **Confirmation Instead Of Reversal** [block] — An "Are you sure?" dialog is a speed bump, not a safeguard — users confirm the action they believe they are taking, so the dialog passes exactly when the user is already wrong. Only a reversal path bounds the damage after the mistaken confirm. TRIGGER: A diff or spec guards a destructive, irreversible, or broadcast-to-others action with a confirmation dialog, checkbox, or type-to-confirm — and no undo window, recall, dry-run, or reversal path is specified.
- **Piggyback Channel Ignored** [note] — Early on you cannot afford to create demand, only to intercept it, which means the cheapest first channel is wherever your users are already aggregated and transacting. Teams skip this because owned channels (blog, newsletter, own social account) feel more legitimate — but those start at zero audience and compound too slowly to survive the runway. TRIGGER: A GTM plan whose channel list contains only owned surfaces (own blog, own newsletter, own social account, own docs site) and names no existing venue, marketplace, forum, or community where the target users already gather.
- **Global Blast Radius** [block] — Treating rules, content, or config as "not code" routes it around the staged rollout that protects code, so a bad artifact reaches 100% of the fleet in one push. If the failure mode also prevents the machine from booting, there is no remote path to roll back. TRIGGER: A change shipping to all users, machines, or tenants simultaneously — or a data/config/rules/prompt/template update path that bypasses the canary and staged-rollout used for code.
