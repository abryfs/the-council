# p12

**Prompt:**
> what's the right postgres index for `WHERE team_id = $1 AND created_at > $2 ORDER BY created_at DESC LIMIT 50`? composite or two separate?

_Context: Mechanical database question during a feature build_


## Candidates (8, ranked by lexical match)

- **Org Chart Shipped To Users** [warn] — A split that mirrors an internal boundary — separate app, brand, login, repo, or team — makes users pay the cost of a structure that exists for the builders' convenience. Users experience one job; splitting it forces them to re-onboard into a second product to accomplish what was previously one motion. TRIGGER: A split, rename, or separation in the product mirrors an internal boundary (two teams, two repos, two services, two panes) and forces the user to move between surfaces to complete one task.
- **Distributed Monolith** [warn] — Splitting a codebase into services that share a release cadence and shared libraries converts in-process function calls into network calls without decoupling deploys, so you pay partial-failure, latency, and operational cost while keeping every coupling you had. TRIGGER: A spec proposing a separate service, worker, repo, or deployable per entity/destination/integration, or a diff introducing an RPC boundary between two things that ship together.
- **Interface Without A Contract** [warn] — When two components exchange bare numbers or strings, the meaning (unit, timezone, encoding, ID namespace) lives only in each side's head. Nothing at the boundary can detect disagreement, so the mismatch propagates as plausible-looking data instead of an error. TRIGGER: A new API field, event payload, or cross-team/cross-service boundary passing raw numbers, timestamps, identifiers, or strings with no shared type, unit, or validation at the boundary.
- **The Never-Restarted Subsystem** [warn] — Long-lived services grow past the scale their cold-start path was designed for, and because that path never runs, the regression is invisible until the day you need it. Recovery time then becomes an unknown discovered during the outage. TRIGGER: A design involving a long-lived stateful service, cache, or index, where warm-up, rebuild, replay, or cold-start time is unstated or assumed fast.
- **Cofounder Equity Without Vesting** [block] — Equity granted without vesting or a cliff prices a contribution before it has happened, and the grant survives the contributor's departure, disagreement, or non-performance. The dispute surfaces at the financing or acquisition that makes the equity worth litigating, which is the worst possible moment to have it. TRIGGER: A cofounder split, advisor grant, contractor equity arrangement, or early-employee offer is described with a percentage but no vesting schedule, cliff, or repurchase right.
- **Foundation Before First User** [block] — Infrastructure built for a feature that does not exist has no consumer to falsify its design, so its interface is derived from imagination and calcifies before contact. The dependent feature then inherits constraints from a substrate that was never tested against the real requirement. TRIGGER: A spec adds infrastructure — an index, cache, schema, consolidation pass, worker, centroid set, router — whose only named consumer is a feature not yet built or validated.
- **Guessing The Bottleneck** [warn] — Intuition about performance is trained on the code you read, while cost lives in behavior you cannot see — allocation, cache misses, scheduler and GC intervals, tail latency. Optimizing before profiling spends effort on the wrong axis and hides the real cause behind a changed baseline. TRIGGER: A diff or plan doing performance work — caching, batching, async, index, language/runtime swap — with no profile, benchmark, or production measurement cited, or a claim that something "should be faster".
- **The Great Rewrite** [block] — A rewrite discards the accumulated bug fixes encoded in the old code — each ugly branch is a defect someone found in production — while the old system keeps needing maintenance, so the team pays for two systems and ships neither. TRIGGER: A prompt or issue proposing to "rewrite from scratch", "start clean", "greenfield it", or replace a working subsystem wholesale because the code is messy.
