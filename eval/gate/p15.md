# p15

**Prompt:**
> the test suite takes 11 minutes and about one in five runs fails on something unrelated to the change. I'm starting to just rerun until green which is obviously bad. fix the flakes first or speed it up first?

_Context: Test suite has become slow and flaky, blocking merges_


## Candidates (8, ranked by lexical match)

- **No Beachhead** [warn] — A message aimed at everyone is specific to no one, so it fails the only test that matters early: can one user explain it to the next user in a sentence. Without a defined first customer, price, channel, and objection-handling all become guesses, and there is no dense population in which word of mouth can propagate. TRIGGER: TAM-driven sizing, "for any team / any company / everyone who...", or a launch plan listing three or more personas with no ranking of which one ships first.
- **Root Cause Singular** [warn] — Five-whys terminates at the first cause that is both technical and fixable, because that node is where the search stops feeling productive. The organizational conditions that let the technical fault reach production are upstream of that stopping point, so they survive the fix and reproduce it. TRIGGER: An incident writeup, postmortem, or bug analysis names exactly one root cause and one code-level fix, with no finding about how the defect passed review or shipped.
- **Launch Without Load** [block] — Capacity assumptions that are never measured are wrong in the unsafe direction, because designers estimate from the intended usage rather than the arrival pattern. Load appears as a step function at launch, not a ramp, so the first real test is also the first outage. TRIGGER: A ship/launch date with no load or soak test in the plan, or a stated concurrency/throughput number that is an estimate rather than a measurement.
- **Exit Reason Assumed** [note] — Churn explanations default to the most legible variable — price, salary, performance — because it is the one already instrumented. The actual reasons are relational and only obtainable by asking, so the retention fix targets the wrong lever and produces no change, which is then read as the problem being intractable. TRIGGER: An explanation of attrition, churn, drop-off, or non-adoption asserts a cause (price, speed, missing feature) without citing anything the departed users or teammates actually said.
- **Control Plane Inside The Blast Radius** [block] — When the tooling that observes, deploys, authenticates, or rolls back depends on the system it manages, the first failure removes the means of recovery. Mean time to repair is then set by whatever out-of-band path was never built. TRIGGER: A design where monitoring, deploy, auth, feature flags, or the rollback path runs on, resolves through, or authenticates against the same system it controls.
- **Single Channel Concentration** [warn] — A channel that supplies most of your users has a ceiling set by audience size and a decay curve set by fatigue and competitive entry, and both arrive without warning. Because the channel is working, nobody funds a second experiment until the first one flattens — at which point there is no runway to discover the replacement. TRIGGER: A growth model that extrapolates the current dominant channel's conversion rate forward, or a plan where one channel already supplies most users and no second-channel experiment is funded and dated.
- **One-Way Door Misread** [block] — Anything external parties can build against — a public API, tool name, URL scheme, event type, wire field, file format — becomes unrevocable the moment someone depends on it, because the cost of removal is paid by them and shows up as broken trust rather than a rollback. Such decisions get made at the speed of a reversible one because the diff looks small. TRIGGER: A diff or spec publishes something external parties will depend on: a public API endpoint, an MCP or CLI tool name, an event type or enum value, a URL scheme, a config key, an on-disk or wire format.
- **Hype Ahead Of Usability** [warn] — A long, expert-narrated demo can make an unexplainable product look compelling to an audience primed to be impressed, and invite scarcity converts that impression into signups. Neither tests the actual constraint — whether one ordinary user can explain the product to the next one — so the waitlist converts into a cohort that opens it once and never returns. TRIGGER: A launch plan gated by waitlist or invite codes, or a demo script/video longer than about two minutes that requires narration to make the product legible.
