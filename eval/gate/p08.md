# p08

**Prompt:**
> why is this regex not matching? `^[\w.-]+@[\w-]+\.[a-z]{2,}$` — it fails on foo+bar@sub.example.co.uk and I don't see why

_Context: Debugging a validation function that keeps rejecting valid input_


## Candidates (8, ranked by lexical match)

- **Product Without Distribution** [block] — Product quality and reach are independent variables, and quality has no mechanism to produce reach on its own — a plan composed entirely of product work therefore converges on an excellent thing nobody can find, while the burn clock runs at the same rate either way. TRIGGER: A plan, sprint, or milestone is entirely product surface — polish, refactor, design review, quality bar — with no line item for how anyone discovers, installs, or is onboarded to it, or the distribution path is known to 404.
- **Premature Automation** [warn] — Automating a process before doing it manually encodes a guess about the rules into code, and the code then prevents you from observing the exceptions that would have taught you the real rules. Manual work at small N is not a stopgap, it is the only instrument that reads the requirement. TRIGGER: A spec automates onboarding, setup, matching, curation, routing, or support before that process has been performed by hand enough times to have written down the exception cases.
- **No Beachhead** [warn] — A message aimed at everyone is specific to no one, so it fails the only test that matters early: can one user explain it to the next user in a sentence. Without a defined first customer, price, channel, and objection-handling all become guesses, and there is no dense population in which word of mouth can propagate. TRIGGER: TAM-driven sizing, "for any team / any company / everyone who...", or a launch plan listing three or more personas with no ranking of which one ships first.
- **The Inside-View Estimate** [warn] — An estimate built by decomposing the specific task counts only the steps you can currently see, and the steps you cannot see are exactly the ones that consume the schedule. Decomposition feels more rigorous than a base rate, so it displaces the base rate rather than being checked against it. TRIGGER: A plan, spec, or roadmap states a duration, ship date, or phase count derived by listing the work, with no reference to how long a comparable past effort actually took.
- **Control Swallowed By Screen** [warn] — A screen control demands visual attention and offers no tactile confirmation, so moving a frequent or eyes-busy action into a menu converts a sub-second muscle-memory operation into a look-navigate-aim-verify loop. The cost is invisible in a demo where the user is already looking at the screen. TRIGGER: A spec relocates a frequent, urgent, or eyes-busy control into a screen, menu, submenu, command palette, or gesture — replacing a dedicated key, button, or always-visible affordance.
- **Parity Roadmap** [warn] — Building a feature because a competitor has it imports their strategy and their constraints without their distribution, and a checklist match gives an existing user of the incumbent no reason to switch — matching is by definition not a differentiator. It also consumes the scarce build capacity that would have produced one. TRIGGER: A requirement is justified by a competitor having it — 'X ships this', 'table stakes', 'we need parity', a feature-comparison matrix, or a decision that would change if that competitor disappeared.
- **Feature Parity Positioning** [warn] — Positioning your product as a better version of an incumbent asks the customer to compare on the incumbent's chosen axes, where the incumbent's scale wins by construction, and it gives no one a reason to bear switching cost. Parity is also unbounded work: matching the feature list is a treadmill the incumbent sets the speed of. TRIGGER: A positioning doc, landing page, or spec that frames the product as "X but better/faster/cheaper", or leads with a feature-comparison table against a named incumbent.
- **Guessing The Bottleneck** [warn] — Intuition about performance is trained on the code you read, while cost lives in behavior you cannot see — allocation, cache misses, scheduler and GC intervals, tail latency. Optimizing before profiling spends effort on the wrong axis and hides the real cause behind a changed baseline. TRIGGER: A diff or plan doing performance work — caching, batching, async, index, language/runtime swap — with no profile, benchmark, or production measurement cited, or a claim that something "should be faster".
